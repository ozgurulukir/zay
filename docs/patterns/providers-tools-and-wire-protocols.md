### Provider polymorphism pattern

Unify static builtin `config_mod.Provider`, dynamic `modelsdev.Provider`, and user-defined `config_mod.ProviderConfig` handles using `ProviderHandle = union(enum) { builtin, dynamic, config }` in `src/tui/widgets/provider_picker.zig`. All three share the same accessor surface (`id()`, `displayName()`, `description()`, `defaultBaseUrl()`, `requiresApiKey()`, `catalogueIndex()`). Since the 2026-09-04 builtin-provider unification, `modelsdev.Provider` is a direct alias of `config_provider.ProviderDef` and the registry carries no local builtin table — the single compile-time catalogue is `builtin_providers` (18 entries) in `src/config/provider.zig`, and `loadBuiltins()` returns it zero-copy; keep new provider metadata in that table only. The `/connect` picker builds a single merged list via `buildMergedProviderList` in `src/tui/provider_model.zig`: builtin catalogue → models.dev registry (overrides builtins with same id) → config providers (overrides everything with same name, **except** entries already covered by the models.dev registry — a `reg.lookup(cp.name)` guard prevents the persisted `ProviderConfig` entry from shadowing the `.dynamic` handle and converting the provider to a "custom" entry in the picker).

### Provider key masking pattern

The `/connect` setup form (`drawForm` in `src/tui/widgets/provider_picker.zig`) masks the API key with `maskSecret` (one `•` per grapheme) so a secret is never rendered in plaintext on screen. The mask is lifted **only while the user is actively editing** the field: `State.key_dirty` flips to `true` on the first real edit (text/codepoint/backspace in `ProviderPicker.handle`, `command_router.zig`; **and** on paste in `pasteToFocusedInput`, `clipboard_helper.zig`, which bypasses the router) and the live input renders in plaintext so a pasted key is verifiable. A pre-filled existing key (form opened to edit) stays masked until the first keystroke. `key_dirty` is reset on every form open (`State.reset()` and `openProviderEntryForm`), so the mask always returns when the form closes — there is no persistent "reveal" toggle. Do not re-mask while typing: that would defeat paste verification, the whole point of the plaintext-while-editing behavior.

### System clipboard pattern

`src/clipboard.zig` handles OS clipboard reading/writing via terminal OSC 52 sequences (`\x1b]52;c;<base64>\x07`) with OS-native execution fallback (`wl-copy`/`xclip`/`pbcopy`/`powershell` via `bash.zig`). `clipboard_helper.zig` routes clipboard data dynamically to focused input fields and transcript message blocks.

### Settings lifecycle pattern

`src/tui/settings_lifecycle.zig` manages pending tabbed form edits, syncs values to `app.cached_config` in real-time, and serializes user settings on `Ctrl+S`. `saveSettings` writes only settings-managed fields (`use_responses_endpoint`, `system_prompt`, `bash_classifier_url`, `toast.enabled`) — never provider/model — and always to the **global** config only (`mergeAndWriteGlobal`; settings are user-level preferences, not project-specific configuration). This prevents project-level provider/model overrides from leaking into global config. The General tab holds the `use_responses_endpoint` and `toast.enabled` toggles; reasoning is not a settings-panel concern — it is controlled per-model via the model picker and persisted session-scoped (see **Reasoning effort lifecycle pattern**). Write-time validation mirrors the parser: `validateSystemPrompt` counts UTF-8 code points against the shared `config.max_system_prompt_chars` (a byte-length check would falsely reject a CJK prompt three bytes per char), and an invalid value is refused at BOTH commit (Enter — a transcript notice now explains why nothing was committed) and save (Ctrl+S). `mergeAndWriteGlobal`/`mergeAndWriteProject` refuse with `error.ConfigRoundTripLoss` when the on-disk re-read produces diagnostics (invalid JSON, over-limit `systemPrompt`/plugin `settings`): the re-read already dropped those values, so an unchecked rewrite would erase them from disk with no signal — the file is left untouched and the caller surfaces the failure. A cleared field is encoded as an empty pending string (`null` means untouched): `applyTextOverlay` maps an empty update to field removal and `serialize` never writes `""`, so Delete-key clears actually reach disk. Tests: `"mergeAndWriteGlobal refuses to rewrite a config that would lose fields"`, `"validateSystemPrompt counts UTF-8 code points like the parser"`, `"clearCurrentField marks a set field cleared and dirty"`.

### Bounded classifier fetch pattern (`src/tools/bash_safety.zig`)

The remote safety-classifier call (`classifyOverSocket`) is a hand-rolled, deadline-bounded HTTP/1.1 exchange over a raw socket — NOT `std.http.Client`. It polls the socket with the remaining budget (`receiveResponseBounded`) into a fixed 16 KiB buffer, frames the response by EOF (`Connection: close`, which the uvicorn sidecar honours), and fails open to the local matcher on timeout/oversize/malformed responses — the same fail-open contract as every other classifier failure. The AI wire clients remain on `std.http.Client`; their shared transport wraps the `Io.Threaded` read callback on POSIX so the `EAGAIN` from `SO_RCVTIMEO` becomes `error.Timeout` instead of Zig 0.16.0's `errnoBug` panic in Debug / `error.Unexpected` in ReleaseFast. That timeout applies to the response body after its head; connect and response-head reads remain on the standard client's unbounded path. Windows and `https://` classifier URLs keep the plain `fetch` exchange without a deadline (documented in `docs/wiki/SAFETY_CLASSIFIER.md`). The classifier deadline is receive-only — send (blocking stream write) and connect (kernel-default; `Io.Threaded.netConnectIpPosix` panics on `ConnectOptions.timeout`, a std TODO) remain unbounded, matching the pre-deadline behavior.

### MCP Server & Tool Discovery pattern

`src/mcp/manager.zig` merges `mcp_servers` configuration across global/project layers (supporting `mcp_servers`, `mcpServers`, and `mcp` JSON aliases) into `McpClient` objects. Transports are `union(enum) { stdio, sse }`; the `{env:VAR}` security model, async-connect lifecycle (`ConnectJob`/`drainConnects`/`installConnectResult`), timeouts, tool injection, and crash isolation are documented in [MCP](../mcp/README.md#3-connection-lifecycle). The `McpMode.handle` routing in `command_router.zig` maps `Up`/`Down`/`j`/`k` to navigation, `Space`/`Enter` to toggle, `Ctrl+R`/`r` to re-sync, `d` to disconnect, `a` to add a remote server by URL (a `State.adding` sub-state fed by the `input_buffers.mcp_url` buffer; the single new entry is persisted to global `config.json` best-effort, while toggling only changes the current process; URL-only, no headers), and `Esc`/`q` to close.

- **`McpClient.stop()` must free a `.failed` reason.** `stop` clobbers `lifecycle` to `.disabled`; if the client carries an owned failure reason (set via `setError`), free `lifecycle.failed.reason` **before** overwriting the lifecycle, or the reason leaks silently (`deinit` calls `stop` before its `failed`-arm switch, so the switch can never see it). Caught by the async-connect tests.

- **MCP registry records own a DEEP-COPIED schema (2026-09-14).** `buildMcpTool` (`src/mcp/registry_bridge.zig`) clones the client's `McpTool.schema` into the record's `*McpToolKey` (`Schema.clone` in `tools/common.zig`), and `freeMcpToolKey` frees it. `disconnectClient`/`reconnectClient` free the client-side schema while the client STAYS in `clients.items`, and the registry cleanup (`syncMcpTools`) is gated off by `anyLaneTurnActive` while `injectToolsInto` still runs — a record borrowing the client schema would dangle through every `tools_json` rebuild and schema-validation read mid-turn. Never store a borrowed `Schema` in a registry record; the record's lifetime must be independent of the client's. MCP transports/protocol/injection: [[MCP]].

### Lua Plugin System pattern

`src/lua/` implements a full Lua 5.4 plugin SDK. `PluginManager` (manager.zig) discovers plugins from `~/.config/zay/plugins/` (global) and project-local roots, loads manifests (`plugin.lua`), and creates sandboxed Lua states. The repository's `plugins/` directory contains the checked-in distribution catalog; TUI installs go to the global directory, not the current checkout. The `App` struct holds `plugin_manager: lua_mod.PluginManager` and `tool_registry: *tools.ToolRegistry`; the `/plugins` TUI overlay lists loaded plugins with active/inactive status and browses bounded JSON store catalogs. The development guide, `zay.*` bridge-function reference, and examples live in [Plugins](../plugins/README.md) / [API reference](../plugins/api-reference.md).

- **Lua sandbox instruction budget is per-dispatch, not per-session.** `resetInstructionBudget(L)` (`src/lua/sandbox.zig`) zeroes the instruction count and re-arms the timeout deadline before each tool call / event dispatch (`callToolHandler` in `plugin_api.zig`, `drainEventCallbacks` in `manager.zig`). Without it the count is a session accumulator and a busy plugin eventually fails every call with "instruction limit exceeded" for the rest of the session. The hook reads its state via `lua_getextraspace` hook data; the timeout check runs every 1000 instructions.

- **Lua Plugin Sandbox, Memory & Require Safety:** `zay.require(mod_path)` resolves strictly within `plugin_dir` (enforced via `std.fs.path.resolve` + prefix and separator boundary check) and caches modules in `LUA_REGISTRYINDEX["zay_loaded_modules"]` with a sentinel `true` to prevent circular-require infinite recursion. `State.raiseError` formats into a stack buffer (`[512]u8`) before calling `lua_error` (zero heap allocations before longjmp). `globMatchSegment` treats `/` and `\` interchangeably for cross-platform path matching. `deletePath` verifies `clean_path != cwd` to protect the project root from deletion. On Windows, plugin and prompt discovery probes `%APPDATA%\zay\plugins` before falling back to `.config\zay\plugins`. Plugin-authoring docs: [[plugins/README]].

### Plugin event wiring pattern

`zay.on(event, callback)` subscribes to lifecycle events by storing callback refs in each plugin's `"zay_events"` Lua registry table. Events are emitted by `Agent.ExecutorBridge` at tool-call boundaries — `onStarted`/`onFinished` (agent.zig) call `plugin_manager.emitEvent(.{ .tool_call_started = ... })` / `.tool_call_finished`. `PluginManager.emitEvent` (manager.zig) iterates every active plugin and drains its `"zay_events"` sub-table for the event name, pcalling each stored callback ref with the payload pushed as a Lua table via `events.pushEventData`. This multi-state dispatch (one Lua state per plugin) replaced the old single-state `EventBus` struct, which was dead code. Event types: `turn_started`, `turn_ended`, `tool_call_started` (`{name, call_id}`), `tool_call_finished` (`{name, call_id, success}`), `response_received`, `plugin_loaded`, `plugin_unloaded`. Reentrancy is safe because the agent worker is single-threaded and emits at tool-call boundaries (after the plugin's own handler has returned).

### Plugin glob matcher pattern

`zay.find_files(root, pattern, opts?)` walks `root` recursively and matches each file's relative path against a glob pattern via `matchGlob` (implemented in `src/lua/bridges/search.zig`, re-exported from `plugin_api.zig` where its 8-test suite lives). Supports `**` (spans directories), `*` (within a segment, does not cross `/`), `?` (one char). The matcher is segment-aware: `src/*.ts` does not match `src/nested/a.ts` (only `*` not `**`), but `**/*.ts` matches at any depth. max_results cap is `max_search_results` (200), with `find_files_default_max_results` = 100 (note `search_files` defaults to 50); gitignore is NOT honored (use `run_bash` with `rg --files` if needed). `matchGlob` is public for unit testing; the 8-test suite covers empty/literal/star/double-star/question-mark cases.

- **Glob/pattern slicing:** Never unconditionally slice byte 0 off a user-supplied pattern (`fp[1..]`). When the pattern is empty, `fp[1..0]` is an out-of-bounds slice → Zig panic → `SIGABRT`. Lua treats `""` as truthy, so a plugin forwarding `file_pattern = ""` reaches this path directly. Extract suffix logic into a pure `fileNameMatches(name, pattern)` helper that handles empty (match-all), `"*x"` (strip leading star), and bare-suffix cases, and unit-test the empty case explicitly.

### Skill subsystem pattern

`src/skill.zig` owns project/global skill discovery, system-prompt publication, and `$name` invocation expansion. `loadProject(gpa, io, home_dir, cwd)` scans two roots — `<home>/.agents/skills` (global, optional) then `<cwd>/.agents/skills` (project) — each via `loadFromDir` (depth-capped at `max_skill_depth = 8`). A project skill with the same name displaces its global counterpart (`shadowDuplicates`, mirroring `plugin_prompt.replaceOrAppend`); two same-name project (or two global) skills both load, first-wins for `find`, and are surfaced by `warnDuplicateNames`.

**Name validation:** `isValidSkillName` enforces `[a-z0-9]+(-[a-z0-9]+)*`, at most 64 bytes. Invalid skills are skipped with a warning (`error.InvalidSkillName`). The description cap, quote/block-scalar rejection, and `zay --strict` rules are documented in [Skills](../SKILLS.md). Loose root `.md` files fall back to their file stem for a name; `SKILL.md` files fall back to their directory name. **Injection budget:** `promptPrefix` enforces a cumulative `max_total_invocation_bytes` (256KB) across all invoked skills; `appendSkillBlock` checks the budget against `stat.size` *before* allocating and returns `error.SkillBudgetExhausted`. **Graceful degradation:** `promptPrefix` catches every non-OOM `appendSkillBlock` error and writes `[skill '<name>' could not be loaded: <err>]` inline instead of failing the turn. **Case-insensitivity:** `find`/`collectInvocations` match skill names case-insensitively (`std.ascii.eqlIgnoreCase`), aligning invocation with the popup (`filterNames`). **Frontmatter parser:** `frontmatterValue` skips indented (nested) lines so nested YAML keys can't shadow top-level ones; block-scalar indicators (`|`, `>`, `|-`, `>-`, `|+`, `>+`) are rejected (`error.BlockScalarUnsupported`). **XML escaping:** `appendSkillBlock` (user-message blocks) routes attribute values through `writeXmlEscaped` (SSOT); `formatForPrompt` (system-prompt skill list) renders markdown bullets (`- **name** — description`) instructing the model to load skills on demand via the builtin `skill` tool (`src/tools/skill.zig`), while users can invoke upfront with `$name`. **Resume markers:** `collectInjectedSkillNames` parses `<skill name="…">` markers without XML unescaping (TD-14); the restricted name charset makes that safe. It reads markers from user messages so `rebuildTranscriptFromAgent` (transcript_lifecycle.zig) restores `[SKILL]` rows on resume. **Palette visibility:** the `/skills` command (`formatSkillsList`) lists every loaded skill with name, description, and path.

- **Skill buffers freed on every path.** `loadOne` and `appendSkillBlock` (`src/skill.zig`) both use a plain `defer gpa.free(raw)` registered immediately after the alloc — never `errdefer` (which leaks on the success path). The buffer is read from disk (up to 256KB per skill) and only the frontmatter values are duped into the returned `Skill`/written into the prompt; without the defer, loading N skills leaks N×256KB per runtime creation and each `$skill` invocation leaks per turn. Registered *before* the `try readSliceAll`, the defer also covers a failed read.

- **Skill invocation dedup must match `find`'s case sensitivity.** `find` is case-insensitive (`eqlIgnoreCase`), so `collectInvocations`'s `contains` helper must also be case-insensitive. If `contains` uses exact `mem.eql`, a prompt like `$Tiger and $tiger` passes both tokens through, and `promptPrefix` injects the same skill body twice — wasting tokens and confusing the model. Keep `contains` and `find` in lockstep.

### Plugin prompt injection pattern (`prompt.md`)

Each plugin directory MAY ship an optional `prompt.md` describing how the model should use that plugin's tools. `src/plugin_prompt.zig` scans `<home>/.config/zay/plugins/*/prompt.md`, the legacy `<cwd>/.zay/plugins/*/prompt.md`, and the current project root `<cwd>/plugins/*/prompt.md` (loaded last, so it wins). Each body is capped at 32 KB per plugin. The markdown bodies are injected into the system prompt as a `<plugin_prompts>` block by `plugin_prompt.formatForPrompt`, appended in `context/assembly.zig` `assembleSystemPrompt` step 5 — parallel to the `SKILL.md` → `<available_skills>` flow. This is a **pure text scan, no Lua state** — it runs early in `runtime.zig` `initSession` (alongside skill loading), before `PluginManager`/`App.initRuntime` create any Lua states. Because `assembleSystemPrompt` bakes the prompt once, plugin prompts reach the model via `system_prompt` only; a freshly-added `prompt.md` takes effect on the next session/lane. The scan mirrors `PluginManager`'s directory conventions but is intentionally decoupled — a plugin with `prompt.md` but no `plugin.lua` still contributes prompt text, and a plugin with `plugin.lua` but no `prompt.md` contributes none. Plugins whose body is empty after frontmatter stripping are skipped (uniform `error.FileNotFound` path).

### Plugin tool dispatch via ToolRegistry pattern

Plugin tools registered through `zay.register_tool` are materialized as `tools.Tool` records in `src/lua/registry_bridge.zig` and inserted into the `ToolRegistry` via `provider_model.registerPluginTools(self)`. Each `Tool` carries a `*PluginToolKey` in its `userdata` field; the shared `runPluginTool`/`displayPluginTool` dispatchers decode the key and route the call to the correct `(plugin_name, tool_name)` handler through `PluginManager.callTool`. The `*const fn` signature on `Tool.run`/`display` is preserved by passing `userdata: *anyopaque` as the last argument — the dispatcher `@ptrCast`s back to a `*PluginToolKey`. `Tool.userdata_free: ?*const fn (gpa, *anyopaque) void` lets the registry release each tool's heap-allocated state. The App's `initRuntime` calls `registerPluginTools` right after `plugin_manager.loadAll()`, which puts the tools in the registry. Plugin tools still use the `lua__<plugin>__<tool>` naming convention so the model can disambiguate them. `executor.runOne` dispatches every non-`mcp__` call through `tool_registry.all(...)` + `tools.runWith` — no `lua__` prefix branch.

**Tool visibility to the model:** a client only advertises tools that are in its serialized `tools_json`. The client is built at `attach` time, but the registry (which carries plugin tools) is set on the agent afterwards — so the freshly-attached client would otherwise keep its builtin-only `tools_json` and never learn about `lua__<plugin>__*` / `mcp__<server>__*` entries. `runtime.replaceClient` guards its `updateTools` rebuild on `tool_registry != null`: during `initSession` (applyFromConfig — every `/new`, `/resume`, lane spawn) the App hasn't wired the registry yet, so rebuilding with a null registry and the empty builtin override would serialize `"[]"` and wipe the builtin tool definitions (shell/lane/background) `init` just built. `createRuntime` (session_switcher.zig) closes the gap for freshly-created runtimes: after wiring `agent.tool_registry` / `mcp_manager` / `plugin_manager`, it calls `provider_model.injectToolsInto` to push the merged tool list (builtin + plugin + MCP) into the new client in one shot. The `OwnedClient.updateTools` union helper dispatches to all three concrete clients (`codex_responses`/`openai_compatible`/`responses_core`); the runtime assembles the final list in `syncToolJson`/`assembleToolSpecs` (runtime.zig). `injectAllTools`/`refreshMcpTools` (provider_model.zig) push MCP+plugin schemas again on `/mcp` and `/plugins` open, toggle, and reconnect. Without the `createRuntime` push, the new session's main client ran tool-less until an unrelated MCP event — the user-visible symptom was `openai_compatible: sending request with NO tools (tools_json is empty)` on every turn. Since the 2026-09-13 re-architecture `tools_json` has ONE owner — `AgentRuntime.syncToolJson`: `assembleToolSpecs` combines registry builtin + plugin + MCP records via `registry.all()` (first-wins by name; static builtin registry when `agent.tool_registry` is still null) and pushes through `LanguageModel.updateTools` (`inline else` structural dispatch). The old `builtin_override` param, the 5×-duplicated `updateMcpTools`, and `AgentRuntime.mcp_tools`-injection for serialization are GONE — MCP tools reach the model the same way they reach dispatch (registry `Tool` records). The compaction/naming clients are INTENTIONALLY tool-less (`tools = &.{}`, never `updateTools`-ed) — the `no_tools client model= url=` info line from them is benign. Regression tests: `"attach during initSession keeps builtin tools when registry is unwired"`, `"attach rebuilds tools from the registry once it is wired"`, `"createRuntime wires the full tool set into the freshly-attached client"` (runtime.zig).

### Plugin tool parameter parsing

`callToolHandler()` in `plugin_api.zig` parses the JSON arguments string into a Lua table before calling the handler, using `pushJsonToLua()` / `pushJsonValue()` which recursively convert `std.json.Value` to Lua values (objects → tables, arrays → 1-indexed tables, strings/numbers/booleans → corresponding Lua types). Plugin handlers receive `params` as a proper Lua table — `params.depth`, `params.pattern`, etc. work directly without manual JSON parsing. `pushJsonValue` is `pub` (not private) because `zay.json_decode` reuses the same Zig-JSON→Lua conversion — do not re-implement it.

- **Bridge integer-clamp idiom.** When a Lua-supplied integer flows into a `u32` field, clamp on the `i64` *before* the `@intCast` so a negative value can't wrap to ~4e9: `@intCast(@max(v, 1))` for positive-only params, `@intCast(@max(v, 0))` for "0 = unlimited" params. For capped params, wrap the clamp in `@min(..., cap)`. See `searchFiles`/`findFiles`/`runBash` (`plugin_api.zig`) and `parsePermissions` (`manifest.zig`).

### Two-store lazy-load plugin pattern (todo plugin)

When a plugin manages both a compact list (frequently read, shown on every call) and bulky detail records (rarely needed, large), keep them in **separate stores** so the list view never pulls the detail into context. The todo plugin is the reference: `.zay/todos.txt` holds the todo.txt task list (one line per task, editable in any editor, spec-portable), while `.zay/todos/plans.json` holds detailed plans (`{summary, steps[], notes}`) keyed by a stable `id:N` tag. `todo_list` reads only `todos.txt` and shows a `[plan:N steps]` *marker* (count, not body); the full plan is fetched on demand via `todo_get_plan(id)`. This is the context-hygiene boundary: a 16-task list costs one short line each, and a multi-hundred-token plan enters context only when the model is actively working on that one task. Three implementation rules: (1) the list store stays plain-text/editable (don't bury it in JSON); (2) the detail store uses `zay.json_encode(plans, {pretty=true})` so it is human-readable and round-trips cleanly via `zay.json_decode`; (3) the key linking them is a stable identifier persisted in the list store itself (the `id:N` todo.txt key:value tag — promoted to `t.id` in `parse_line`), NOT the array index, because `table.remove` shifts indices on delete while ids stay valid across edits. `load_todos()` reads fresh from disk on every call (no `_G.todos` cache across turns) so external edits to `todos.txt` are always reflected — the old cache-once behavior masked out-of-band edits. `load_plans()` returns `{}` on missing-or-corrupt so a bad sidecar never blocks the task list.

### Plugin bridge function pattern

All `zay.*` bridge functions are C-callable `lua_CFunction` registered in the `zay` global table by `registerPluginApi()` in `sandbox.zig`. Each function receives `?*c.lua_State`, extracts arguments via `bridge.pullValue()`, performs the operation through Zay's safe Zig APIs (path validation via `sanitizePath()`, shell execution via `pwsh_exec` / `bash_exec`), and returns results as Lua values. The `std.Io` instance is stored in the Lua registry (`zay_io`) for filesystem access. Currently 29 bridge functions across 6 categories: Filesystem (11: `read_file`, `write_file`, `edit_file`, `search_files`, `find_files`, `list_dir`, `file_info`, `mkdir`, `copy_path`, `move_path`, `delete_path`), Shell & Env (5: `run_shell`, `run_bash`, `get_env`, `get_cwd`, `get_project_root`), Git (6: `git_status`, `git_diff`, `git_log`, `git_branch`, `git_add`, `git_commit`), Plugin System (4: `require`, `register_tool`, `on`, `think`), JSON (2: `json_decode`, `json_encode`), plus `shell_quote`. The registration table in `sandbox.zig` is the source of truth when adding more. Relative module loading is provided via `zay.require(mod_path)` (scoped strictly to plugin directory and cached in `zay_loaded_modules`). The JSON bridges — `zay.json_decode(str)` and `zay.json_encode(value, opts?)` — let plugins parse and emit structured data without hand-rolling a parser or shelling out to `jq`. `json_decode` reuses `pushJsonValue` (Zig `std.json.Value` → Lua); `json_encode` traverses the Lua value with `lua_next`, inferring array vs object from key shape (`lua_rawlen == lua_next` entry count → array `[...]`, else object `{...}`), and writes to an allocating writer with optional `{pretty=true}` for indent_2 output. Empty tables serialize as `[]` (the common plugin convention for an empty list). Functions/userdata/threads (no JSON form) emit `null` rather than failing the whole encode. The encode helpers (`writeLuaValueJson`/`writeTableJson`/`writeTableAsArray`/`writeTableAsObject`) share an explicit `JsonWriteError = std.Io.Writer.Error` to break the inferred-error-set dependency loop created by their mutual recursion.

- **Plugin cwd resolution:** All plugin cwd resolution goes through
  `bridge.resolvePluginCwd` (`src/lua/bridge.zig`), which reads
  `plugin_cwd_slot` (lane worktree OR `/resume` session cwd) or falls back to
  the process cwd. Never call `std.process.currentPathAlloc` directly in a
  bridge.
- **Event callback cwd window:** Plugin event callbacks (`on_started`/`on_finished`)
  run inside `runAll`'s `plugin_cwd_slot` window, set around the whole batch
  and refreshed by `rerootFromRequester` on mid-batch lane ops. This ensures
  fs/shell/git bridges called from event handlers see the correct effective cwd.

Plugin cwd resolution uses `bridge.resolvePluginCwd` (`src/lua/bridge.zig`) and the derived binding above, never `std.process.currentPathAlloc`. The effective cwd may be a lane worktree or a resumed session root; the process cwd remains the launch directory.

- **Lua C-stack manipulation:** When building a Lua table of results from Zig, the results table must stay on top of the stack across every entry. The correct idiom is `newTable()` (push table) → push entry fields + `lua_setfield(L, -2, ...)` → `lua_rawseti(L, -2, n)` (pops the entry, leaving the table on top). A stray extra push before `lua_rawseti` with the wrong table index (`-3` instead of `-2`) writes the bare integer into `results[n]` instead of the entry table and **leaks one table per match** onto the stack. Annotate the expected stack layout (`[ ... | results_table ]`, `[ ... | results_table | entry ]`) at each push/pop site so the balance is auditable.

- **`sanitizePath` realpath re-check mirrors `validateCwd`.** `sanitizePath` (`plugin_api.zig`) does a lexical `startsWith(cwd)` check, then a best-effort `std.c.realpath` re-check so a symlink escaping the project root is caught. `realpath` returns null on ENOENT (a new file being written), so fall back to the lexical verdict on null — never reject a legitimately-new path. This mirrors the bash tool's `validateCwd`. `sanitizePath` (the `bridges/shell.zig` SSOT, re-exported by fs.zig) also rejects C0 control bytes (`< 0x20`) with `error.InvalidPath`: NT returns `OBJECT_NAME_INVALID` for them and std's Io layer *panics* on that status in Debug, so a plugin path with an embedded control character (e.g. a `\t` that survived a Lua string literal — backslash paths in Lua scripts become escapes) must be rejected at the boundary instead of crashing the host. Corollary: never embed a native backslash path into a Lua script string; use forward slashes.

### Tool schema strict-mode pattern

OpenAI strict structured-outputs mode (`"strict":true`, `additionalProperties:false`, `required:[all properties]` with optionals made nullable) is **opt-in via `ai.Config.strict` (default `false`)** — it only works against the OpenAI API and silently breaks function-calling on gateways (OpenRouter/Ollama/vLLM/Together), which causes the model to emit tool calls as plain text (`<function=...><parameter=...>`) instead of `tool_calls` deltas. Tool-definition serialization lives in a **single** place: `src/ai/tool_schema.zig` — `buildAllToolsJson`/`writeToolDefinition`/`writeParameters` thread `strict: bool` end-to-end and take an `Envelope{completions,responses}` that encodes the only wire-format difference (Chat Completions wraps each definition in a `"function"` object; Responses emits it flat). `openai_compatible.zig` calls it with `.completions`, `responses_core.zig` with `.responses`. The `Client.strict` field captures strict at `init` so `updateTools`/`syncToolJson` rebuilds `tools_json` consistently. The inline golden test (`tool_schema golden: byte-identical output…`) locks the produced bytes for both envelopes × strict on/off — the closure-brace count per envelope is easy to get wrong, so the golden is the regression guard. When `strict` is off: the `"strict"` key is omitted (the leading comma before `"parameters"` is still written so the JSON stays valid), and `required` lists only genuinely-required properties. The setting flows `config.strict_outputs: ?bool` → `AgentRuntime.strict_outputs` (set at session init and re-synced from `cached_config` at every connect) → `.strict = self.strict_outputs` set once on the unified attach path (`attachClients`/`createAttachClient`, runtime.zig); secondary compaction/naming clients force `strict = false` via `attachSecondaryConfig`. Enable it with `"strictOutputs": true` in config.json or `ZAY_STRICT_OUTPUTS=1`. There is **no provider auto-detection** — defaulting strict off keeps tool-calling working everywhere; OpenAI direct users opt in explicitly.

**Persistence:** `strict_outputs` is a global (API-level) setting, not model-scoped, so it is **not** carried on `ModelSelection`/`BuiltinSelection`/`CustomSelection` (unlike `use_responses_endpoint`/`enable_thinking`/`system_prompt`/`bash_classifier_url`). `parseObject` therefore does **not** clear `out.strict_outputs` when building `model_selection` (the four model-scoped settings are cleared), leaving it on `config` for `serialize` to read. `serialize`'s `model_selection` branch (the production path) must read `config.strict_outputs` directly and write `strictOutputs` — the earlier code wrote it only in the legacy branch (`model_selection == null`, i.e. tests), so the setting vanished on the next save in normal operation and reset to `false` on restart.

### Background jobs & agent tool pattern

Zay manages asynchronous, long-running processes launched with `run_in_background: true` via `BackgroundManager` (`src/background.zig`). The AI model queries and controls these jobs through the builtin `background` tool (`src/tools/background.zig`, with operations `list`, `status`, `cancel`, `tail`). Bounded reverse file reading (`readLogTailBounded` in `src/tools/background.zig`, scanning at most the trailing 64 KB, skips leading UTF-8 continuation bytes, and tolerates missing or non-existent files gracefully across Windows and POSIX.

### Shared shell-tool pipeline pattern (`shell.zig` + `capture_sink.zig`)

`src/tools/shell.zig` owns the tool-side pipeline shared by the twin shell tools, generic over a comptime `Backend` namespace (`Impl(comptime B)`; the contract is enforced by `validateBackend`'s `@hasDecl`/`@TypeOf` + `@compileError` checks — extend the contract there, never by specializing one backend). ### Tool argument validation pattern

`ExecutorService.runOne` validates every tool call's `arguments` JSON against the tool's `tools_common.Schema` **before dispatch**, in a single choke point shared by all three channels (builtin / plugin / MCP): `resolveSchema` finds the schema (MCP via `mcp__<server>__<tool>` parse + `full_name` match against connected clients; builtin/plugin via one registry `all()` lookup), and `src/tools/schema.zig`'s pure `validateArgs` produces a `ValidationResult` whose violations become a structured model-facing error (`Invalid arguments for tool 'bash': \`command\` is required`) instead of letting the tool run on garbage. `validateArgs` converts every non-OOM failure (parse error, wrong type, missing field, null-when-not-nullable, enum miss) into a violation internally, so the only error it propagates is `OutOfMemory` — `runOne` does `catch return error.OutOfMemory`. Type rules: JSON integers satisfy both `integer` and `number`; floats only `number`; quoted `"42"` is neither; `std.json.Value.number_string` (an i64-overflowing JSON number token) counts as a number. Unknown tools (no schema) skip validation. v1 does **not** check `additionalProperties` or nested object/array element schemas. `runValidationError` is separate from `runFailure` (execution errors) and leaves it untouched; tests cover all three channels plus a positive control.

### Retry/backoff pattern (shared `ai/transport.zig`, both wire clients)

`ai.Config` carries `max_retries` (default `2`) and `retry_base_delay_ms` (default `500`) — `max_retries = 0` is the legacy single-attempt kill-switch. Since the 2026-09-13 transport unification this loop lives in `ai/transport.zig::Transport.prompt` and is SHARED by both wire clients: the payload is serialized **once** per cache mode through the `PayloadSource` writer (`openai_request.writeRequestPayload` for chat — the production path; `responses_request` for Responses), then `sendOnce` loops; only head-phase failures are retried while attempts remain: 429 (`error.HttpRateLimited`), 5xx (`error.HttpServerError`), and connection drops classified by `headPhaseFailure` as `error.ConnectionFailed` (socket errors plus `error.HttpConnectionClosing` — std.http's report for reusing an idle keep-alive connection the server already closed). Every other 4xx is permanent (schema/auth/model errors don't self-heal) and stream-mid errors never surface as these codes, so partial deltas are never double-delivered. `Retry-After` (integer seconds, case-insensitive, parsed from `http_response.head.bytes` *before* the body reader is initialized — head pointers die at body start) takes precedence over exponential backoff `base * 2^attempt`, which is capped at 8000 ms. The mock-server tests (`MockRetryServer` over `std.Io.net` ephemeral-port listen/accept + `std.http.Server`) exercise 503→200, 429→200, permanent-4xx no-retry, retry exhaustion, and the kill-switch — the retry decision, delay computation, and header parsing are also covered by pure unit tests.

**C2 cache-downgrade retry (added 2026-08-06; homed in `ai/transport.zig` since the unification):** a 400 whose error body mentions "cache" (`Transport.errorDetailMentionsCache`, case-insensitive) earns exactly ONE cache-stripped re-send — the `PayloadSource.writePayload` callback re-serializes with `disable_prompt_cache = true` (drops OpenRouter `cache_control` + `session_id`, OpenAI `prompt_cache_key`) and the FULL 429/5xx retry budget is replayed on the stripped payload. This is a *separate* failure mode from 429/5xx, so it's decoupled from the `attempt` counter via a `downgrade_done` one-shot gate and an outer `while (true)` loop that runs at most twice (original + stripped). Zig's `while … : (step) { continue }` runs the step expr, so riding the counter would burn a user-facing retry slot. The downgrade is gated on `!disable_cache` (no fields to strip if the user already disabled caching) and on `err == error.HttpClientError` (only a 400 — not 429/5xx). Conservative "cache" substring match; a false positive costs one extra request and then fails normally.

### Outbound provider headers pattern (`provider_headers.zig`)

Single source of truth for headers on an outbound AI request: the INV-RESP-1 sibling leaf `src/ai/provider_headers.zig`, imported by the shared `Transport` (`src/ai/transport.zig`, whose `sendOnce` both `openai_compatible` and `responses_core` drive through `transport.prompt`, with per-request headers materialized by `Transport.materializeHeaders`), the codex profile table, and the `/v1/models` probe — never through each other. It owns the spec type (`Header{name, HeaderValue}` where `HeaderValue = literal | session_id | account_id`, aliased back into `ResponsesConfig` so the codex profile table compiles unchanged), the merge policy (`build`), and the zero-alloc per-request materializer (`HeaderSet` over a `[max_outbound_headers]` stack buffer, which every send site sizes; `8 profile + 8 user + 3 auto`). Two header classes flow through it: **auto** headers a provider requires/merits — the OpenCode Zen routing pair `x-opencode-session` (value = the 32-hex session id, resolved per request from the client-owned `config.session_id`) + `x-opencode-client: zay`, both mandatory on `opencode.ai/zen*` URLs since 2026-09-05, and the OpenRouter attribution `X-Title: Zay` (migrated from the chat client's deleted `app_title`/`app_referer` fields) — and **user** headers from `providers.<name>.headers` (MCP-style `{env:VAR}` raw-on-disk, expanded at attach time by `config/provider.zig::expandProviderHeaders`). Precedence is resolved in exactly one place, inside `build`: a user header whose name matches an auto header (ASCII case-insensitive) replaces it; non-colliding user headers follow in config order. Zen routing headers are transport identity, NOT cache hints: `build` never sees `disable_prompt_cache`, so the flag cannot suppress them. Data flow: `parseProviderHeaders` (validation: name must be token-safe single-line, value non-empty single-line; reserved transport names — `authorization`, `content-type`, `host`, `content-length`, `transfer-encoding`, `connection` — rejected with a warn; capped at 8) → `ProviderConfig.headers` → runtime `buildProviderHeaders` (`expandProviderHeaders` + `build`, resolved once per attach — headers frozen until the next attach, mirroring MCP connect-time expansion) → `ai.Config.headers` (BORROWED; both clients deep-dupe via `provider_headers.cloneHeaders` into `provider_headers_owned`, freed in `deinit`) → `HeaderSet.append` per request. The Responses client appends its static protocol profile (codex handshake set) BEFORE the provider set, so profile headers win name collisions (`accept`/`OpenAI-Beta` are functional, not styling). The chat compaction/naming clients now carry `session_id` too (the old gap left the zen session header empty on summarizer/branch-naming traffic). The models probe builds its own specs from the URL (`listModels(..., Options{session_id, user_headers})` — job-owned session-id dupe in `model_loader.Job`, because the App may switch sessions while the background probe runs). Serialization writes headers back RAW (placeholders preserved) — a settings save never leaks a resolved secret.

### Zero-copy historical pruning pattern

`Agent.run` sends `client.prompt` a `[]const ai.MessageView` (defined in `ai.zig`) instead of a deep copy of the history: `pruneHistoricalToolResultsViews` (context/assembly.zig) BORROWS every unchanged message straight from the ContextManager (`.borrowed: *const ChatMessage` — base64 images are never re-duped per turn) and only historical tool messages older than the keep-recent cutoff become `.owned` pruned copies. `freePrunedViews` frees only `.owned`; borrowed views alias live manager memory and are valid for the duration of the synchronous `prompt` call because the manager appends only after it returns (`takeAssistantMessage`/`takeToolResults`). The pointer-identity test asserts an image's `data_base64.ptr` is identical to the source — the proof that no copy happened. All `LanguageModel` tags except `.none` (three wire clients + the `scripted` test adapter) and both payload writers consume views; do not reintroduce whole-history cloning. `cloneContentBlock` remains only as the block-copy helper inside `pruneSingleToolMessage`. `Agent.run` passes configurable `keep_recent_tool_turns` and the shared `tool_output_cap_bytes` (`context.compaction.keepRecentToolTurns` / `toolOutputCapBytes`). The same byte cap is applied by `ExecutorService` before any built-in, Bash/Pwsh, database, plugin, or MCP result enters history; larger results are stored and represented by a head+tail excerpt plus a database retrieval handle. The database tool can search saved text for a literal and return chunk/character offsets before reading a bounded window. Twelve recent tool-result turns remain untouched by historical pruning by default; older full results already present in a session are head-tail pruned to the configured cap.

**Head+tail sandwich truncation (SSOT: `common.elideMiddle`).** Historical pruning (`pruneSingleToolMessage` → `common.pruneToolText`) and compaction's summarizer render (`cappedToolResult`) both truncate an oversized tool result as a head+tail sandwich — first half of the budget + last half, joined by `common.elideMiddle` with a `[... N of M bytes elided to save context ...]` marker — instead of head-only. Head-only truncation dropped the load-bearing conclusion (errors, test results, `rg` hits, `git status`) that lives at the tail, forcing the model to re-run commands to rediscover it. The bash spill `Full output:` footer sits at the very end and survives naturally inside the tail. `at_mention` file ingestion uses the same `elideMiddle` SSOT to read a mention's REAL head+tail (first half + last half of the 64 KB budget) so an oversized plan keeps its conclusion, with a `[file truncated: N bytes — re-read via shell if you need the rest]` notice. Do not reintroduce head-only truncation at any of these sites.

- **Historical tool-result pruning must never prune everything when no turn exceeds budget.** `computeCutoff` (assembly.zig) counts a contiguous `.tool` run as **one turn** (increments only at run end), so a parallel batch of 8 tools counts as 1 turn. When `cutoff_index == messages.len` (no turn exceeds the keep budget), the old code pruned the entire history; guard with `pruning_active = cutoff_index < messages.len` in `pruneHistoricalToolResultsViews`. Keep `estimatePrunedTokensRange` in lockstep by reusing `computeCutoff` over the full slice.

### Job(T) async-family pattern (`src/tui/job.zig`, 2026-09-19)

The six App-level async families — diff refresh, models.dev registry refresh, model load, codex login, git label, plugin store (`JobFamily`, `src/tui/lifecycle.zig`) — previously each hand-rolled a future + done-atomic pair. `Job(T)` owns the lifecycle once: `spawn(io, ctx, comptime worker)` arms through the `io.concurrent` transport and stores `done` LAST with `.release`, so the UI thread polls `isDone()` non-blockingly. Invariants: (a) **arm-first** — the owning union/optional is assigned FIRST and only then armed through a pointer into its final address, because the spawned task captures `&self.done`; the owner may not reassign the slot until `adopt()`/`cancel()` returns. Spawn failure resets the pair to disarmed, so the caller's fallback (move the union out, re-raise) never leaves an armed state with an undefined future; (b) **ADOPT CONSUMES THE JOB** — after `adopt` the owner discards the slot; a re-spawn on a consumed slot Debug-panics; (c) `cancel` is a blocking join for teardown only, never the render path. `anyJobActive`/`cancelAllJobs` are an exhaustive `inline for` over `std.meta.fields(JobFamily)` wired into both the tick check and teardown cancel — adding a family arm without both is a compile error, not a silent deadlock. Per-family behavior (debounce, generation/session drops, adopt protocol, result projection) stays in `git_label_job.zig` / `codex_login_job.zig` / `registry_job.zig` / `model_loader_job.zig` / `diff_lifecycle.zig` / `plugin_store_job.zig`; `git label` + `codex login` dropped their `std.Thread.spawn` heap jobs in favor of `Job(T)`. Regression tests: `"job spawns, polls, and adopts exactly once"`, `"job cancel joins a blocked worker and discards the result"`, `"adopt consumes the job: a fresh slot is required for the next run"` (job.zig).

Every `Tool.run`/`Tool.display` callback receives `Tool.Env{ctx, userdata}`: `ctx` is the executor-owned runtime record (lane bridge + requester, background manager + owner generation, skills, plugin manager, classifier URL, MCP manager), `userdata` the per-tool state (plugin tools carry a `*PluginToolKey`; builtins leave it `undefined`). ### Lane turn lifecycle spine (`src/tui/turn_lifecycle.zig`, 2026-09-19; folded 2026-09-24)

One private `spawnTurn` spine (reset → model → `turn.submit` → stale-free/set → `io.concurrent(runAgentTurn)`) sits behind ALL three starters: `beginSubmit` (the user-submit front door — gates, projection, then one `spawnTurn(.{.prompt})` call; returns true = worker spawned, so `App.startTurn` is DELETED and the old two-phase `beginSubmit`+`startTurn` window where the machine was `.active` with no worker cannot be re-created by a future caller), `startQueuedTurn` (ESC restart + background completion delivery), and `startTurnForLane` (model-driven spawn; title/naming derive from `title_source`, not the framed prompt). `projectCancelNotice` is shared by the ESC interrupt path (async teardown via `beginTurnCancel`'s `TurnCancelJob`) and `cancelLaneTurn` (`lane cancel`, synchronous) — the ESC-async vs lane-cancel-sync fork stays explicit. `convergeFinishedTurn` (checkpoint + queued restart) is shared by the worker-event path and `drainTurnCancels` so the two convergence orderings cannot drift. Invariants: `startQueuedTurn` gates on the AGENT queue, not the UI mirror (the mirror can be empty while the agent queue holds entries); `beginSubmit` is queue-first (`turn.isActive() or cancel_job != null` → `enqueueSubmit`) while its C1 guard still preserves typed input (see § Lane engine states for the `worker_context == null` rationale); the projections `beginSubmit` runs BEFORE the spine (transcript row, title, naming, skill mirroring) read nothing the spine's `resetTurnState` clears, so the fold is ordering-safe. **Prompt ownership (flipped 2026-09-24):** `SpawnOpts.prompt` is allocated on the lane worker's allocator and owned by the CALLER until the spawn succeeds — the spine's errdefer only clears the slot claim on failure, the caller's errdefer frees; after success the worker consumes the bytes. **The prompt slot lives on `worker_context.Context` (`agent_worker.PendingPrompt`: `take`/`set`/`freeStale`), not the Thread** — slot and allocator share a lifetime (`parkFinishedWorker` nulls `worker_context`; `Thread.deinit` previously freed worker-gpa bytes with the passed gpa, a latent mismatch that only worked while all allocators alias — they still do today, `root.zig` wires ONE process allocator into `tui_gpa`/`runtime_gpa`/`agent.gpa`, so a "worker gpa ≠ app gpa" assert is unimplementable until lanes get distinct allocators). Handoff is single-writer (UI `set` pre-spawn, worker `take` on entry); R2 audit verdict (2026-09-24): no UI reader touches the slot after the worker steals it — readers are only spawnTurn, the worker, and deinit/park teardown. **Batch queue drain verdict (2026-09-24): skipped** — `drainAllQueuedToHistory`'s per-message costs are @-mention file I/O and per-message session-DB persistence, both inherent; the mutex is never held across that work and the queue caps at 64 entries, so a batched variant would only amortize session writes for a queue that maxes at 64. Regression tests: `"scripted turn runs the real worker end to end and converges to idle"`, `"interrupted turn converges into a scripted queued restart"` (tui/tests.zig).

- **`app.thread` is view focus + input routing only (2026-09-13 de-swap).** Lane-targeted operations take `*Thread` explicitly and must NOT scope-swap `app.thread`: the drain paths (`drainAgentEvents`/`drainTurnCancels`) pass the lane to `applyAgentEvent`/`convergeFinishedTurn`/`checkpointFinishedTurn`; queue/checkpoint helpers (`flushQueuedUserMessagesToTranscript`, `clearQueuedUserMessages`, `appendSkillInvocationsToTranscript`, `sealCheckpoint`) read the lane's transcript and `lane.liveRuntime()` (the per-lane accessor on `Thread`) so a background lane's flush/checkpoint uses ITS runtime, not the viewed lane's; `startTurnForLane(app, lane, prompt, title_source)` and `startQueuedTurn(app, lane)` (`turn_lifecycle.zig`), and `captureLaneContext(app, spawner, max)` all operate on the passed lane. Scope-swaps (`app.thread = lane; defer …`) are forbidden in new code. Focused-lane forwarders on `App` pass `self.thread`.

- **`installRuntime` (session switch) checks only the active lane's turn — by design.** Other lanes keep running against their own runtimes; each lane owns its runtime, so a switch must not tear down lanes still in use. Completion routing is generation-safe across the switch (M1). Documented in `transcript_lifecycle.zig`.

### Lane engine states: idle vs live

`Thread.Engine` is `union(enum) { idle: vcs.Lane, live: Live }` where `Live = { lane: vcs.Lane, runtime: *AgentRuntime, owns: bool }`. Idle lanes — created via `lane create` or rested via `parkFinishedWorker` (which nulls `worker_context`/`agent` and downgrades `engine` to `.idle`) — cannot run a turn until a runtime is attached. `cycleLane` sets `app.thread` to any lane including idle ones — no guard (view focus may be idle). `createRuntime` uses `templateRuntime()` (the first live lane's runtime) as a template and wires the agent fully. Any code that dereferences `worker_context` or `agent` off a lane must guard for the idle case. **One refusal gate** (2026-09-13): `lanes_util.requireLiveRuntime(app)` / `lanes_util.appendIdleLaneNotice(app)` post the pinned "`lane enter` / `lane spawn`" notice (stack-buffered — a refusal must never itself fail); `refuseOnIdleLane` is a thin wrapper and `beginSubmit`'s C1 guard (homed in `turn_lifecycle.zig` since the turn consolidation) keeps its position BEFORE `toOwnedSlice` (TD-2, preserves typed input) with the guard condition `worker_context == null`. Why NOT `engine == .idle` (spelled out, TD-2 doc): `worker_context` is the thing the submit path actually dereferences (`resetCancel`, the worker-gpa prompt dupe), and "idle engine" is a coarser predicate that does not imply it — test fixtures (and the headless path) legitimately construct `.live` engines whose runtimes/worker contexts are unattached or undefined, so an engine-state guard would pass those fixtures straight into a null deref, while the null check refuses exactly the lanes that cannot spawn a worker. Guard the field you use, not the state you assume. `commandNeedsRuntime(command)` (mode_lifecycle) is the exhaustive needs-runtime table for the `.command` submit arm; add every new Command there AND to the enumeration test. Key handlers are unguarded by design: park closes runtime-bound overlays.

### Runtime Genesis & unified client attach (2026-09-19)

`initSession`'s former 10-positional-param contract (a transposition compiles silently) is one named struct — `runtime.Genesis{gpa, io, cwd, session_dir, home_dir, base_system_prompt, config, diagnostics, session_id (?), template (?*const AgentRuntime)}`; `initNew`/`initResume` assert the mode (`session_id == null` starts a session, non-null resumes). `cwd` (tools+skills, a lane's workspace) vs `session_dir` (session DB, always the repo root so all lanes share one DB) are deliberately distinct; `cwd` is owned (duped) because a cross-project resume frees `summary.cwd` on the next picker reload (see § Cross-project session resume pattern). Client attach is ONE plan: `attachClients(AttachPlan)` derives main + compaction + naming roles by copy — `attachSecondaryConfig` is main minus the tool surface (`tools = &.{}`, `strict = false`) plus the role's prompt, and `max_output_tokens` stays unset on secondaries because it serializes as `max_tokens` and a small global cap must never truncate a persisted summary. Main attach is fatal; secondary attach is best-effort (the previous secondary survives). A fourth adapter costs one `AttachAdapter` arm + one `createAttachClient` wrapper, nothing more. Regression test: `"attach parity: every role inherits plan fields across all adapters"` (runtime.zig).

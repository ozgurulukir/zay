# Providers, Tools, and Wire Protocols

> Related pattern pages: [Architecture & Layering](architecture-and-layering.md) · [Plugins, MCP & Skills](plugins-mcp-and-skills.md) · [Configuration, Sessions & Persistence](configuration-sessions-and-persistence.md) · [TUI, Lanes & Worktrees](tui-lanes-and-worktrees.md)

### Provider key masking pattern

The `/connect` setup form (`drawForm` in `src/tui/widgets/provider_picker.zig`) masks the API key with `maskSecret` (one `•` per grapheme) so a secret is never rendered in plaintext on screen. The mask is lifted **only while the user is actively editing** the field: `State.key_dirty` flips to `true` on the first real edit (text/codepoint/backspace in `ProviderPicker.handle`, `command_router.zig`; **and** on paste in `pasteToFocusedInput`, `clipboard_helper.zig`, which bypasses the router) and the live input renders in plaintext so a pasted key is verifiable. A pre-filled existing key (form opened to edit) stays masked until the first keystroke. `key_dirty` is reset on every form open (`State.reset()` and `openProviderEntryForm`), so the mask always returns when the form closes — there is no persistent "reveal" toggle. Do not re-mask while typing: that would defeat paste verification, the whole point of the plaintext-while-editing behavior.

### Bounded classifier fetch pattern (`src/tools/bash_safety.zig`)

The remote safety-classifier call (`classifyOverSocket`) is a hand-rolled,
deadline-bounded HTTP/1.1 exchange over a raw socket — not `std.http.Client`.
It polls the socket with the remaining budget (`receiveResponseBounded`) into
a fixed 16 KiB buffer, and frames the response by EOF (`Connection: close`,
which the uvicorn sidecar honours). On timeout, oversized or malformed
responses, it falls back to the local matcher. This is the fallback behavior
for classifier failures; the local verdict still decides whether to ask for
approval.

The AI wire clients remain on `std.http.Client`; their shared transport wraps
the `Io.Threaded` read callback on POSIX so `EAGAIN` from `SO_RCVTIMEO` becomes
`error.Timeout` instead of Zig 0.16.0's `errnoBug` panic in Debug or
`error.Unexpected` in ReleaseFast. That timeout applies to the response body
after its head; connect and response-head reads remain unbounded. Windows and
`https://` classifier URLs use the standard fetch path without this explicit
deadline. The classifier deadline covers receiving only; send and connect
remain unbounded. See the [Safety & Classifier Guide](../wiki/SAFETY_CLASSIFIER.md)
for user-facing behavior and setup.

### Tool schema strict-mode pattern

OpenAI strict structured-outputs mode (`"strict":true`, `additionalProperties:false`, `required:[all properties]` with optionals made nullable) is **opt-in via `ai.Config.strict` (default `false`)** — it only works against the OpenAI API and silently breaks function-calling on gateways (OpenRouter/Ollama/vLLM/Together), which causes the model to emit tool calls as plain text (`<function=...><parameter=...>`) instead of `tool_calls` deltas. Tool-definition serialization lives in a **single** place: `src/ai/tool_schema.zig` — `buildAllToolsJson`/`writeToolDefinition`/`writeParameters` thread `strict: bool` end-to-end and take an `Envelope{completions,responses}` that encodes the only wire-format difference (Chat Completions wraps each definition in a `"function"` object; Responses emits it flat). `openai_compatible.zig` calls it with `.completions`, `responses_core.zig` with `.responses`. The `Client.strict` field captures strict at `init` so `updateTools`/`syncToolJson` rebuilds `tools_json` consistently. The inline golden test (`tool_schema golden: byte-identical output…`) locks the produced bytes for both envelopes × strict on/off — the closure-brace count per envelope is easy to get wrong, so the golden is the regression guard. When `strict` is off: the `"strict"` key is omitted (the leading comma before `"parameters"` is still written so the JSON stays valid), and `required` lists only genuinely-required properties. The setting flows `config.strict_outputs: ?bool` → `AgentRuntime.strict_outputs` (set at session init and re-synced from `cached_config` at every connect) → `.strict = self.strict_outputs` set once on the unified attach path (`attachClients`/`createAttachClient`, runtime/connection.zig); secondary compaction/naming clients force `strict = false` via `attachSecondaryConfig`. Enable it with `"strictOutputs": true` in config.json or `ZAY_STRICT_OUTPUTS=1`. There is **no provider auto-detection** — defaulting strict off keeps tool-calling working everywhere; OpenAI direct users opt in explicitly.

**Persistence:** `strict_outputs` is a global (API-level) setting, not model-scoped, so it is **not** carried on `ModelSelection`/`BuiltinSelection`/`CustomSelection` (unlike `use_responses_endpoint`/`enable_thinking`/`system_prompt`/`bash_classifier_url`). `parseObject` therefore does **not** clear `out.strict_outputs` when building `model_selection` (the four model-scoped settings are cleared), leaving it on `config` for `serialize` to read. `serialize`'s `model_selection` branch (the production path) must read `config.strict_outputs` directly and write `strictOutputs` — the earlier code wrote it only in the legacy branch (`model_selection == null`, i.e. tests), so the setting vanished on the next save in normal operation and reset to `false` on restart.

### Background jobs & agent tool pattern

Zay manages asynchronous, long-running processes launched with `run_in_background: true` via `BackgroundManager` (`src/background.zig`). The AI model queries and controls these jobs through the builtin `background` tool (`src/tools/background.zig`, with operations `list`, `status`, `cancel`, `tail`). Access to `BackgroundManager` flows through the executor's typed context seam: `ExecutorService` wires a `BackgroundStart{manager, owner_generation}` option into `Tool.Context` (executor.zig) and every tool callback receives it via `Tool.Env{ctx}` as `ToolContext.background_manager` (`src/tools/context.zig`) — there are no thread-local slots. Bounded reverse file reading (`readLogTailBounded` in `src/tools/background.zig`, scanning at most the trailing 64 KB, skips leading UTF-8 continuation bytes, and tolerates missing or non-existent files gracefully across Windows and POSIX.

### Shared shell-tool pipeline pattern (`shell.zig` + `capture_sink.zig`)

`src/tools/shell.zig` owns the tool-side pipeline shared by the twin shell tools, generic over a comptime `Backend` namespace (`Impl(comptime B)`; the contract is enforced by `validateBackend`'s `@hasDecl`/`@TypeOf` + `@compileError` checks — extend the contract there, never by specializing one backend). The per-shell modules (`bash.zig`, `pwsh.zig`) keep only real divergence as Backend decls and re-export `Impl`'s pub surface unchanged (`tool`, `runTool`, `runContained`, `runBackground`, `wantsBackground`, `BackgroundCtx`, the `display_diff_*` sentinels): name/description/prompt prefix, the exec module, the containment guard script (`cd`/`pushd`/`popd` overrides vs `Set-Location`/`Push-Location`/`Pop-Location`), background `CommandMode` + stderr-merge wrapper, and `validateCwd` — the bash (lexical prefix + best-effort realpath) vs pwsh (`paths.pathsEqual` slash/case-tolerant) split is SEMANTIC, do not fold it. `currentEnvMap`'s login-env overlay dissolves rather than parameterizes: both `bash_exec.loginEnvBlock` (null on Windows) and `pwsh_exec.loginEnvBlock` (always null) already answer correctly, so the shared code calls `B.exec.loginEnvBlock(io)` unconditionally. Process-capture machinery (bounded rolling tail, spill `Sink`, `drainChild`, `Result`/`Capture`/`CaptureLimits`) lives in `tools/capture_sink.zig`; the spill prefix/dir is injected through the `Sink(comptime config)` namespace so it imports neither exec module. Exec modules re-export the shared types under their old names, so `BackgroundManager`/`clipboard`/`plugin_api`/`root.zig` keep resolving. `registry.shell_tool` (comptime `os.is_windows` pick) stays the bash↔pwsh SSOT. `Sink.finish()` consumes the sink (tail + spill path move into `Capture`) — pair `deinit` only with the error path. `lua/plugin_api.zig`'s `countLines` is a DELIBERATE semantic variant of the shared observation counter (empty → 1 line, no trailing-newline compensation); do not unify.

- **Bash & PowerShell containment (`bash.zig`, `pwsh.zig`, `shell.zig`, `#642`):** `validateCwd` (`src/tools/bash.zig`) keeps the cwd inside the project root, comparing against a **normalized** root (trailing slash can't defeat it) plus a best-effort realpath re-check so a symlink escaping the root is caught (realpath failure → lexical verdict). In `bash.zig`, `cd_guard_functions` marks `_zay_root` `readonly` and checks `"${_phys#"$_zay_root"/}" = "$_phys"` (when `"$_zay_root" != "/"`) so sibling-prefix paths (e.g. `/repo-evil` from `/repo`) cannot escape; `pwsh.zig` marks `_zay_root` `-Option Constant` and registers `Function:\Set-Location`, `Push-Location`, `Pop-Location` with `-Options Constant` using `StartsWith("$root\", OrdinalIgnoreCase)`. `pwsh_exec.zig` opens script temp files with `.exclusive = true` and `0600` permissions, and `shell.zig` passes `display_command` (without the prepended guard script) to `finishOutput`. The destructive-command gate is **always armed**: `bash_safety.classify` takes an optional URL and runs the local matcher when none is configured. Background job logs use unpredictable names (`zay-bg_<id>-<hex>.log` plus an exclusive create) and spill/temp files use hex-only names; stale `zay-bash-*` / `zay-bg_*` files older than 24h are pruned at startup; spills cap at 10MB.
- **Database tool protected-table guard (`src/tools/database.zig`, `#642`):** `containsProtectedResultTable` tracks parenthesized table expressions and subqueries inside `FROM` clauses so `SELECT * FROM (tool_results)` or `SELECT * FROM (SELECT * FROM tool_results)` cannot bypass the private artifact-table guard.

- **`runContained*` never classifies — the caller proves it.** `runContained`/`runContainedWithCancellation` (`src/tools/shell.zig`) perform no command classification; they require a `bash_safety.ClassifiedCommand` token, minted via `executor_safety.mintClassified` after the approval gate (`shouldRejectUnsafeShell`) classifies and approves (#295). Current callers: the executor's shell-tool branch (lane workers — a null mint there is refused at runtime with `error.UnclassifiedContainedRun`) and the `skill` tool's command mode, which receives the same mint through the tool context (`ToolContext.shell_gate_mint`, set per dispatch by the executor and cleared after; an ungated caller is refused with `error.UnclassifiedSkillCommandRun` — the registry `Tool.run` signature cannot carry the token as a parameter). Do not fold classification into `runContained*` — the executor already classified by the time it dispatches, so inline classification would double-prompt on remote-classifier flaps. See the [Safety & Classifier Guide](../wiki/SAFETY_CLASSIFIER.md) for the full classified/not-classified surface.

### Tool argument validation pattern

`ExecutorService.runOne` validates every tool call's `arguments` JSON against the tool's `tools_common.Schema` **before dispatch**, in a single choke point shared by all three channels (builtin / plugin / MCP): `resolveSchema` finds the schema (MCP via `mcp__<server>__<tool>` parse + `full_name` match against connected clients; builtin/plugin via one registry `all()` lookup), and `src/tools/schema.zig`'s pure `validateArgs` produces a `ValidationResult` whose violations become a structured model-facing error (`Invalid arguments for tool 'bash': \`command\` is required`) instead of letting the tool run on garbage. `validateArgs` converts every non-OOM failure (parse error, wrong type, missing field, null-when-not-nullable, enum miss) into a violation internally, so the only error it propagates is `OutOfMemory` — `runOne` does `catch return error.OutOfMemory`. Type rules: JSON integers satisfy both `integer` and `number`; floats only `number`; quoted `"42"` is neither; `std.json.Value.number_string` (an i64-overflowing JSON number token) counts as a number. Unknown tools (no schema) skip validation. v1 does **not** check `additionalProperties` or nested object/array element schemas. `runValidationError` is separate from `runFailure` (execution errors) and leaves it untouched; tests cover all three channels plus a positive control.

### Retry/backoff pattern (shared `ai/transport.zig`, both wire clients)

`ai.Config` carries `max_retries` (default `2`) and `retry_base_delay_ms` (default `500`) — `max_retries = 0` is the legacy single-attempt kill-switch. Since the 2026-09-13 transport unification this loop lives in `ai/transport.zig::Transport.prompt` and is SHARED by both wire clients: the payload is serialized **once** per cache mode through the `PayloadSource` writer (`openai_request.writeRequestPayload` for chat — the production path; `responses_request` for Responses), then `sendOnce` loops; only head-phase failures are retried while attempts remain: 429 (`error.HttpRateLimited`), 5xx (`error.HttpServerError`), and connection drops classified by `headPhaseFailure` as `error.ConnectionFailed` (socket errors plus `error.HttpConnectionClosing` — std.http's report for reusing an idle keep-alive connection the server already closed). Every other 4xx is permanent (schema/auth/model errors don't self-heal) and stream-mid errors never surface as these codes, so partial deltas are never double-delivered. `Retry-After` (integer seconds, case-insensitive, parsed from `http_response.head.bytes` *before* the body reader is initialized — head pointers die at body start) takes precedence over exponential backoff `base * 2^attempt`, which is capped at 8000 ms. The mock-server tests (`MockRetryServer` over `std.Io.net` ephemeral-port listen/accept + `std.http.Server`) exercise 503→200, 429→200, permanent-4xx no-retry, retry exhaustion, and the kill-switch — the retry decision, delay computation, and header parsing are also covered by pure unit tests.

**C2 cache-downgrade retry (added 2026-08-06; homed in `ai/transport.zig` since the unification):** a 400 whose error body mentions "cache" (`Transport.errorDetailMentionsCache`, case-insensitive) earns exactly ONE cache-stripped re-send — the `PayloadSource.writePayload` callback re-serializes with `disable_prompt_cache = true` (drops OpenRouter `cache_control` + `session_id`, OpenAI `prompt_cache_key`) and the FULL 429/5xx retry budget is replayed on the stripped payload. This is a *separate* failure mode from 429/5xx, so it's decoupled from the `attempt` counter via a `downgrade_done` one-shot gate and an outer `while (true)` loop that runs at most twice (original + stripped). Zig's `while … : (step) { continue }` runs the step expr, so riding the counter would burn a user-facing retry slot. The downgrade is gated on `!disable_cache` (no fields to strip if the user already disabled caching) and on `err == error.HttpClientError` (only a 400 — not 429/5xx). Conservative "cache" substring match; a false positive costs one extra request and then fails normally.

### Outbound provider headers pattern (`provider_headers.zig`)

Single source of truth for headers on an outbound AI request: the INV-RESP-1 sibling leaf `src/ai/provider_headers.zig`, imported by the shared `Transport` (`src/ai/transport.zig`, whose `sendOnce` both `openai_compatible` and `responses_core` drive through `transport.prompt`, with per-request headers materialized by `Transport.materializeHeaders`), the codex profile table, and the `/v1/models` probe — never through each other. It owns the spec type (`Header{name, HeaderValue}` where `HeaderValue = literal | session_id | account_id`, aliased back into `ResponsesConfig` so the codex profile table compiles unchanged), the merge policy (`build`), and the zero-alloc per-request materializer (`HeaderSet` over a `[max_outbound_headers]` stack buffer, which every send site sizes; `8 profile + 8 user + 3 auto`). Two header classes flow through it: **auto** headers a provider requires/merits — the OpenCode routing pair `x-opencode-session` (value = the 32-hex session id, resolved per request from the client-owned `config.session_id`) + `x-opencode-client: zay`, mandatory on `opencode.ai/zen*` URLs since 2026-09-05 and on `opencode.ai/inference/go*` URLs (OpenCode Go rejects requests missing the session header with HTTP 400), and the OpenRouter attribution `X-Title: Zay` (migrated from the chat client's deleted `app_title`/`app_referer` fields) — and **user** headers from `providers.<name>.headers` (MCP-style `{env:VAR}` raw-on-disk, expanded at attach time by `config/provider.zig::expandProviderHeaders`). Precedence is resolved in exactly one place, inside `build`: a user header whose name matches an auto header (ASCII case-insensitive) replaces it; non-colliding user headers follow in config order. Zen routing headers are transport identity, NOT cache hints: `build` never sees `disable_prompt_cache`, so the flag cannot suppress them. Data flow: `parseProviderHeaders` (validation: name must be token-safe single-line, value non-empty single-line; reserved transport names — `authorization`, `content-type`, `host`, `content-length`, `transfer-encoding`, `connection` — rejected with a warn; capped at 8) → `ProviderConfig.headers` → runtime `buildProviderHeaders` (`expandProviderHeaders` + `build`, resolved once per attach — headers frozen until the next attach, mirroring MCP connect-time expansion) → `ai.Config.headers` (BORROWED; both clients deep-dupe via `provider_headers.cloneHeaders` into `provider_headers_owned`, freed in `deinit`) → `HeaderSet.append` per request. The Responses client appends its static protocol profile (codex handshake set) BEFORE the provider set, so profile headers win name collisions (`accept`/`OpenAI-Beta` are functional, not styling). The chat compaction/naming clients now carry `session_id` too (the old gap left the zen session header empty on summarizer/branch-naming traffic). The models probe builds its own specs from the URL (`listModels(..., Options{session_id, user_headers})` — job-owned session-id dupe in `model_loader.Job`, because the App may switch sessions while the background probe runs). Serialization writes headers back RAW (placeholders preserved) — a settings save never leaks a resolved secret.

### Zero-copy historical pruning pattern

`Agent.run` sends `client.prompt` a `[]const ai.MessageView` (defined in `ai.zig`) instead of a deep copy of the history: `pruneHistoricalToolResultsViews` (context/prune.zig) BORROWS every unchanged message straight from the ContextManager (`.borrowed: *const ChatMessage` — base64 images are never re-duped per turn) and only historical tool messages older than the keep-recent cutoff become `.owned` pruned copies. `evictHistoryImagesViews` builds the stubbed user message first and frees any replaced `.owned` view on swap so OOM leaves the original intact and replaced views never leak; `estimatePrunedTokensRangeWithSkills` uses `estimateRenderedToolTokens` consistently whether `skills` is null or empty (`#615`). `freePrunedViews` frees only `.owned`; borrowed views alias live manager memory and are valid for the duration of the synchronous `prompt` call because the manager appends only after it returns (`takeAssistantMessage`/`takeToolResults`). The pointer-identity test asserts an image's `data_base64.ptr` is identical to the source — the proof that no copy happened. All `LanguageModel` tags except `.none` (three wire clients + the `scripted` test adapter) and both payload writers consume views; do not reintroduce whole-history cloning. `cloneContentBlock` remains only as the block-copy helper inside `pruneSingleToolMessage`. `Agent.run` passes configurable `keep_recent_tool_turns` and the shared `tool_output_cap_bytes` (`context.compaction.keepRecentToolTurns` / `toolOutputCapBytes`). The same byte cap is applied by `ExecutorService` before any built-in, Bash/Pwsh, database, plugin, or MCP result enters history; larger results are stored and represented by a head+tail excerpt plus a database retrieval handle. The database tool can search saved text for a literal and return chunk/character offsets before reading a bounded window. Twelve recent tool-result turns remain untouched by historical pruning by default; older full results already present in a session are head-tail pruned to the configured cap.

**Head+tail sandwich truncation (SSOT: `common.elideMiddle`).** Historical pruning (`pruneSingleToolMessage` → `common.pruneToolText`) and compaction's summarizer render (`cappedToolResult`) both truncate an oversized tool result as a head+tail sandwich — first half of the budget + last half, joined by `common.elideMiddle` with a `[... N of M bytes elided to save context ...]` marker — instead of head-only. Head-only truncation dropped the load-bearing conclusion (errors, test results, `rg` hits, `git status`) that lives at the tail, forcing the model to re-run commands to rediscover it. The bash spill `Full output:` footer sits at the very end and survives naturally inside the tail. `at_mention` file ingestion uses the same `elideMiddle` SSOT to read a mention's REAL head+tail (first half + last half of the 64 KB budget) so an oversized plan keeps its conclusion, with a `[file truncated: N bytes — re-read via shell if you need the rest]` notice. Do not reintroduce head-only truncation at any of these sites.

- **Historical tool-result pruning must never prune everything when no turn exceeds budget.** `computeCutoff` (context/prune.zig) counts a contiguous `.tool` run as **one turn** (increments only at run end), so a parallel batch of 8 tools counts as 1 turn. When `cutoff_index == messages.len` (no turn exceeds the keep budget), the old code pruned the entire history; guard with `pruning_active = cutoff_index < messages.len` in `pruneHistoricalToolResultsViews`. Keep `estimatePrunedTokensRange` in lockstep by reusing `computeCutoff` over the full slice.

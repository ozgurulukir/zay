### MCP Server & Tool Discovery pattern

`src/mcp/manager.zig` merges `mcp_servers` configuration across global/project layers (supporting `mcp_servers`, `mcpServers`, and `mcp` JSON aliases) into `McpClient` objects. Transports are `union(enum) { stdio, sse }`; the `{env:VAR}` security model, async-connect lifecycle (`ConnectJob`/`drainConnects`/`installConnectResult`), timeouts, tool injection, and crash isolation are documented in [MCP](../mcp/README.md#3-connection-lifecycle). The `McpMode.handle` routing in `command_router.zig` maps `Up`/`Down`/`j`/`k` to navigation, `Space`/`Enter` to toggle, `Ctrl+R`/`r` to re-sync, `d` to disconnect, `a` to add a remote server by URL (a `State.adding` sub-state fed by the `input_buffers.mcp_url` buffer; the single new entry is persisted to global `config.json` best-effort, while toggling only changes the current process; URL-only, no headers), and `Esc`/`q` to close.

- **`McpClient.stop()` must free a `.failed` reason.** `stop` clobbers `lifecycle` to `.disabled`; if the client carries an owned failure reason (set via `setError`), free `lifecycle.failed.reason` **before** overwriting the lifecycle, or the reason leaks silently (`deinit` calls `stop` before its `failed`-arm switch, so the switch can never see it). Caught by the async-connect tests.

- **MCP registry records own a DEEP-COPIED schema (2026-09-14).** `buildMcpTool` (`src/mcp/registry_bridge.zig`) clones the client's `McpTool.schema` into the record's `*McpToolKey` (`Schema.clone` in `tools/common.zig`), and `freeMcpToolKey` frees it. `disconnectClient`/`reconnectClient` free the client-side schema while the client STAYS in `clients.items`, and the registry cleanup (`syncMcpTools`) is gated off by `anyLaneTurnActive` while `injectToolsInto` still runs — a record borrowing the client schema would dangle through every `tools_json` rebuild and schema-validation read mid-turn. Never store a borrowed `Schema` in a registry record; the record's lifetime must be independent of the client's. MCP transports/protocol/injection: [[MCP]].

### Lua Plugin System pattern

`src/lua/` implements a full Lua 5.4 plugin SDK. `PluginManager` (manager.zig) discovers plugins from `~/.config/zay/plugins/` (global) and project-local roots, loads manifests (`plugin.lua`), and creates sandboxed Lua states. The repository's `plugins/` directory contains the checked-in distribution catalog; TUI installs go to the global directory, not the current checkout. The `App` struct holds `plugin_manager: lua_mod.PluginManager` and `tool_registry: *tools.ToolRegistry`; the `/plugins` TUI overlay lists loaded plugins with active/inactive status and browses bounded JSON store catalogs. The development guide, `zay.*` bridge-function reference, and examples live in [Plugins](../plugins/README.md) / [API reference](../plugins/api-reference.md).

- **Lua sandbox instruction budget is per-dispatch, not per-session.** `resetInstructionBudget(L)` (`src/lua/sandbox.zig`) zeroes the instruction count and re-arms the timeout deadline before each tool call / event dispatch (`callToolHandler` in `plugin_api.zig`, `emitEvent` in `manager.zig`). Without it the count is a session accumulator and a busy plugin eventually fails every call with "instruction limit exceeded" for the rest of the session. The hook reads a VM-owned budget via `lua_getextraspace`; the timeout/cancellation check runs every 1000 instructions, including full-access and timeout-only states. Coroutines share the budget, whose registry-rooted userdata stays alive through `lua_close` finalizers. Cleanup retains hooks and caps the remaining finalization deadline at 1000 ms. The vendored `lgc.c` preserves count-only hooks during GC finalizers (upstream suppresses all hooks); GC remains stopped and finalizer errors stay protected. Keep this patch when updating Lua. Resource/cancellation stops are sticky until the host resets the dispatch. Guarded protected calls and bridge boundaries rethrow them outside native cleanup frames. All callbacks for one emission share the remaining event deadline.

- **Lua Plugin Sandbox, Memory & Require Safety:** `zay.require(mod_path)` resolves strictly within `plugin_dir` (enforced via `std.fs.path.resolve` + prefix and separator boundary check) and caches modules in `LUA_REGISTRYINDEX["zay_loaded_modules"]` with a sentinel `true` to prevent circular-require infinite recursion. `State.raiseError` formats into a stack buffer (`[512]u8`) before calling `lua_error` (zero heap allocations before longjmp). `globMatchSegment` treats `/` and `\` interchangeably for cross-platform path matching. `deletePath` verifies `clean_path != cwd` to protect the project root from deletion. On Windows, plugin and prompt discovery probes `%APPDATA%\zay\plugins` before falling back to `.config\zay\plugins`. Plugin-authoring docs: [[plugins/README]].

### Plugin event wiring pattern

`zay.on(event, callback)` subscribes to lifecycle events by storing callback refs in each plugin's `"zay_events"` Lua registry table. Events are emitted by `Agent.ExecutorBridge` at tool-call boundaries — `onStarted`/`onFinished` (agent.zig) call `plugin_manager.emitEvent(.{ .tool_call_started = ... })` / `.tool_call_finished`. `PluginManager.emitEvent` (manager.zig) checks an atomic subscription mask to skip unsubscribed instances without Lua access, then drains its `"zay_events"` sub-table for the event name, pcalling each stored callback ref with the payload pushed as a Lua table via `events.pushEventData`. This multi-state dispatch (one Lua state per plugin) replaced the old single-state `EventBus` struct, which was dead code. Event types: `turn_started`, `turn_ended`, `tool_call_started` (`{name, call_id}`), `tool_call_finished` (`{name, call_id, success}`), `response_received`, `plugin_loaded`, `plugin_unloaded`. Each heap-allocated `PluginInstance` owns an execution mutex: handlers, callbacks and save/restore access its Lua stack exclusively. The guard encloses `pcall` and result copying, so Lua errors cannot skip unlock. Callbacks stay synchronous on the emitting worker and retain its TLS cwd/classifier/cancellation context. Only one instance mutex is held at a time; nested plugin dispatch is unsupported. Different plugin instances remain independent. Tool acquisition is cancelable and bounded to 1000 ms (`PluginBusy` on expiry). Events share a 1000 ms wait/execution budget across subscribed instances, skipping and logging busy instances without replay. Delivered callbacks remain synchronous. Tool metadata is captured during initialization into owned immutable snapshots (`src/lua/tool_snapshot.zig`); registry descriptors deep-copy these snapshots without touching live Lua. `PluginManager.beginUse` pins the generation for whole agent turns, dispatches and metadata copies, while mutations require an exclusive zero-user transition and otherwise return `InFlightTurn`. UI registry replacement still requires all workers, including interrupting workers, to be joined. Manager copies are allowed only before workers are wired; instance addresses remain stable until guarded replacement or teardown.

### Plugin glob matcher pattern

`zay.find_files(root, pattern, opts?)` walks `root` recursively and matches each file's relative path against a glob pattern via `matchGlob` (implemented in `src/lua/bridges/search.zig`, re-exported from `plugin_api.zig` where its 8-test suite lives). Supports `**` (spans directories), `*` (within a segment, does not cross `/`), `?` (one char). The matcher is segment-aware: `src/*.ts` does not match `src/nested/a.ts` (only `*` not `**`), but `**/*.ts` matches at any depth. max_results cap is `max_search_results` (200), with `find_files_default_max_results` = 100 (note `search_files` defaults to 50); gitignore is NOT honored (use `run_bash` with `rg --files` if needed). `matchGlob` is public for unit testing; the 8-test suite covers empty/literal/star/double-star/question-mark cases.

- **Glob/pattern slicing:** Never unconditionally slice byte 0 off a user-supplied pattern (`fp[1..]`). When the pattern is empty, `fp[1..0]` is an out-of-bounds slice → Zig panic → `SIGABRT`. Lua treats `""` as truthy, so a plugin forwarding `file_pattern = ""` reaches this path directly. Extract suffix logic into a pure `fileNameMatches(name, pattern)` helper that handles empty (match-all), `"*x"` (strip leading star), and bare-suffix cases, and unit-test the empty case explicitly.

### Search-tools grep path and output contracts (2026-10-08)

`plugins/packages/search-tools` passes the original file/directory root to both
backends. Native `search_files` stats the sanitized root: exact files are read
once, directories share a fixed root across recursion for relative include
globs. Do not emulate a file search with a recursive basename filter: duplicate
and suffix filenames leak into results, and the filter can overwrite `include`.
Regex mode validates the target via `file_info`, then runs from the active
workspace with the target as an argument. Changing cwd to a relative root while
also passing that root to rg resolves it twice. Parse `rg --json` rather than
colon-delimited output (Windows drive letters and colon filenames). A nonempty
stderr on exit 1 is an error: the PowerShell bridge can map native failures to 1.
Ripgrep ignores include globs on explicit files, so regex mode checks these
targets with `find_files` first. Its exact-file path uses the same basename glob
matcher as native content search, without reading or walking sibling files.
Decode only through the first overflow match and report a lower-bound count.

The package's `test.lua` retains mocked command/error tests and exercises actual
Zay filesystem, shell, quoting and JSON bridges against temporary fixtures. Keep
these integration checks: mocked results previously hid path resolution, exact
file isolation and include-glob failures. Live regex checks require rg; without
it they verify the failure response and print that the live checks were skipped.

### Skill subsystem pattern

`skill` command mode delegates to the host shell's contained foreground pipeline
with the canonical registered skill directory as its execution root. The executor
classifies the original command with that same cwd before dispatch, retaining the
usual observer approval route. Per-call `ZAY_WORKSPACE_CWD` identifies the active
lane/session workspace; neither the executor cwd nor process cwd is changed.
Command outputs are ordinary tool results and are excluded from live activation
and legacy instruction reconstruction. Scripts share shell capture limits,
timeout and cancellation behavior; containment guards location changes only.

`src/skill.zig` owns project/global skill discovery, system-prompt publication, and `$name` invocation expansion. `loadProject(gpa, io, home_dir, cwd)` scans two roots — `<home>/.agents/skills` (global, optional) then `<cwd>/.agents/skills` (project) — each via `loadFromDir` (depth-capped at `max_skill_depth = 8`). A project skill with the same name displaces its global counterpart (`shadowDuplicates`, mirroring `plugin_prompt.replaceOrAppend`); two same-name project (or two global) skills both load, first-wins for `find`, and are surfaced by `warnDuplicateNames`.

**Name validation:** `isValidSkillName` enforces `[a-z0-9]+(-[a-z0-9]+)*`, at most 64 bytes. Invalid skills are skipped with a warning (`error.InvalidSkillName`). The description cap, quote/block-scalar rejection, and `zay --strict` rules are documented in [Skills](../SKILLS.md). Loose root `.md` files fall back to their file stem for a name; `SKILL.md` files fall back to their directory name. **Injection budget:** `promptPrefix` enforces a cumulative `max_total_invocation_bytes` (256KB) across all invoked skills; `appendSkillBlock` checks the budget against `stat.size` *before* allocating and returns `error.SkillBudgetExhausted`. **Graceful degradation:** `promptPrefix` catches every non-OOM `appendSkillBlock` error and writes `[skill '<name>' could not be loaded: <err>]` inline instead of failing the turn. **Case-insensitivity:** `find`/`collectInvocations` match skill names case-insensitively (`std.ascii.eqlIgnoreCase`), aligning invocation with the popup (`filterNames`). **Frontmatter parser:** `frontmatterValue` skips indented (nested) lines so nested YAML keys can't shadow top-level ones; block-scalar indicators (`|`, `>`, `|-`, `>-`, `|+`, `>+`) are rejected (`error.BlockScalarUnsupported`). **XML escaping:** `appendSkillBlock` (user-message blocks) routes attribute values through `writeXmlEscaped` (SSOT); `formatForPrompt` (system-prompt skill list) renders markdown bullets (`- **name** — description`) instructing the model to load skills on demand via the builtin `skill` tool (`src/tools/skill.zig`), while users can invoke upfront with `$name`. **Resume markers:** `collectInjectedSkillNames` parses `<skill name="…">` markers without XML unescaping (TD-14); the restricted name charset makes that safe. It reads markers from user messages so `rebuildTranscriptFromAgent` (transcript_lifecycle.zig) restores `[SKILL]` rows on resume. **Palette visibility:** the `/skills` command (`formatSkillsList`) lists every loaded skill with name, description, and path.

- **Skill buffers freed on every path.** `loadOne` and `appendSkillBlock` (`src/skill.zig`) both use a plain `defer gpa.free(raw)` registered immediately after the alloc — never `errdefer` (which leaks on the success path). The buffer is read from disk (up to 256KB per skill) and only the frontmatter values are duped into the returned `Skill`/written into the prompt; without the defer, loading N skills leaks N×256KB per runtime creation and each `$skill` invocation leaks per turn. Registered *before* the `try readSliceAll`, the defer also covers a failed read.

- **Skill invocation dedup must match `find`'s case sensitivity.** `find` is case-insensitive (`eqlIgnoreCase`), so `collectInvocations`'s `contains` helper must also be case-insensitive. If `contains` uses exact `mem.eql`, a prompt like `$Tiger and $tiger` passes both tokens through, and `promptPrefix` injects the same skill body twice — wasting tokens and confusing the model. Keep `contains` and `find` in lockstep.

### Plugin prompt injection pattern (`prompt.md`)

Each plugin directory MAY ship an optional `prompt.md` describing how the model should use that plugin's tools. `src/plugin_prompt.zig` scans `<home>/.config/zay/plugins/*/prompt.md`, the legacy `<cwd>/.zay/plugins/*/prompt.md`, and the current project root `<cwd>/plugins/*/prompt.md` (loaded last, so it wins). Each body is capped at 32 KB per plugin. The markdown bodies are injected into the system prompt as a `<plugin_prompts>` block by `plugin_prompt.formatForPrompt`, appended in `context/assembly.zig` `assembleSystemPrompt` step 5 — parallel to the `SKILL.md` → `<available_skills>` flow. This is a **pure text scan, no Lua state** — it runs early in `runtime.zig` `initSession` (alongside skill loading), before `PluginManager`/`App.initRuntime` create any Lua states. Because `assembleSystemPrompt` bakes the prompt once, plugin prompts reach the model via `system_prompt` only; a freshly-added `prompt.md` takes effect on the next session/lane. The scan mirrors `PluginManager`'s directory conventions but is intentionally decoupled — a plugin with `prompt.md` but no `plugin.lua` still contributes prompt text, and a plugin with `plugin.lua` but no `prompt.md` contributes none. Plugins whose body is empty after frontmatter stripping are skipped (uniform `error.FileNotFound` path).

### Plugin tool dispatch via ToolRegistry pattern

Plugin tools registered through `zay.register_tool` are materialized as `tools.Tool` records in `src/lua/registry_bridge.zig` and inserted into the `ToolRegistry` via `provider_model.registerPluginTools(self)`. Each `Tool` carries a `*PluginToolKey` in its `userdata` field; the shared `runPluginTool`/`displayPluginTool` dispatchers decode the key and route the call to the correct `(plugin_name, tool_name)` handler through `PluginManager.callTool`. The `*const fn` signature on `Tool.run`/`display` is preserved by passing `userdata: *anyopaque` as the last argument — the dispatcher `@ptrCast`s back to a `*PluginToolKey`. `Tool.userdata_free: ?*const fn (gpa, *anyopaque) void` lets the registry release each tool's heap-allocated state. The App's `initRuntime` calls `registerPluginTools` right after `plugin_manager.loadAll()`, which puts the tools in the registry. Plugin tools still use the `lua__<plugin>__<tool>` naming convention so the model can disambiguate them. `executor.runOne` dispatches every non-`mcp__` call through `tool_registry.all(...)` + `tools.runWith` — no `lua__` prefix branch.

**Tool visibility to the model:** a client only advertises tools that are in its serialized `tools_json`. The client is built at `attach` time, but the registry (which carries plugin tools) is set on the agent afterwards — so the freshly-attached client would otherwise keep its builtin-only `tools_json` and never learn about `lua__<plugin>__*` / `mcp__<server>__*` entries. `runtime.replaceClient` guards its `updateTools` rebuild on `tool_registry != null`: during `initSession` (applyFromConfig — every `/new`, `/resume`, lane spawn) the App hasn't wired the registry yet, so rebuilding with a null registry and the empty builtin override would serialize `"[]"` and wipe the builtin tool definitions (shell/lane/background) `init` just built. `createRuntime` (session_switcher.zig) closes the gap for freshly-created runtimes: after wiring `agent.tool_registry` / `mcp_manager` / `plugin_manager`, it calls `provider_model.injectToolsInto` to push the merged tool list (builtin + plugin + MCP) into the new client in one shot. The `OwnedClient.updateTools` union helper dispatches to all three concrete clients (`codex_responses`/`openai_compatible`/`responses_core`); the runtime assembles the final list in `syncToolJson`/`assembleToolSpecs` (runtime.zig). `injectAllTools`/`refreshMcpTools` (provider_model.zig) push MCP+plugin schemas again on `/mcp` and `/plugins` open, toggle, and reconnect. Without the `createRuntime` push, the new session's main client ran tool-less until an unrelated MCP event — the user-visible symptom was `openai_compatible: sending request with NO tools (tools_json is empty)` on every turn. Since the 2026-09-13 re-architecture `tools_json` has ONE owner — `AgentRuntime.syncToolJson`: `assembleToolSpecs` combines registry builtin + plugin + MCP records via `registry.all()` (first-wins by name; static builtin registry when `agent.tool_registry` is still null) and pushes through `LanguageModel.updateTools` (`inline else` structural dispatch). The old `builtin_override` param, the 5×-duplicated `updateMcpTools`, and `AgentRuntime.mcp_tools`-injection for serialization are GONE — MCP tools reach the model the same way they reach dispatch (registry `Tool` records). The compaction/naming clients are INTENTIONALLY tool-less (`tools = &.{}`, never `updateTools`-ed) — the `no_tools client model= url=` info line from them is benign. Regression tests: `"attach during initSession keeps builtin tools when registry is unwired"`, `"attach rebuilds tools from the registry once it is wired"`, `"createRuntime wires the full tool set into the freshly-attached client"` (runtime.zig).

### Plugin tool parameter parsing

`callToolHandler()` in `plugin_api.zig` parses the JSON arguments string into a Lua table before calling the handler, using `pushJsonToLua()` / `pushJsonValue()` which recursively convert `std.json.Value` to Lua values (objects → tables, arrays → 1-indexed tables, strings/numbers/booleans → corresponding Lua types). Plugin handlers receive `params` as a proper Lua table — `params.depth`, `params.pattern`, etc. work directly without manual JSON parsing. `pushJsonValue` is `pub` (not private) because `zay.json_decode` reuses the same Zig-JSON→Lua conversion — do not re-implement it.

- **Bridge integer-clamp idiom.** When a Lua-supplied integer flows into a `u32` field, clamp on the `i64` *before* the `@intCast` so a negative value can't wrap to ~4e9: `@intCast(@max(v, 1))` for positive-only params, `@intCast(@max(v, 0))` for "0 = unlimited" params. For capped params, wrap the clamp in `@min(..., cap)`. See `searchFiles`/`findFiles`/`runBash` (`plugin_api.zig`) and `parsePermissions` (`manifest.zig`).

### Two-store lazy-load plugin pattern (todo plugin)

When a plugin manages both a compact list (frequently read, shown on every call) and bulky detail records (rarely needed, large), keep them in **separate stores** so the list view never pulls the detail into context. The todo plugin is the reference: `.zay/todos.txt` holds the todo.txt task list (one line per task, editable in any editor, spec-portable), while `.zay/todos/plans.json` holds detailed plans (`{summary, steps[], notes}`) keyed by a stable `id:N` tag. `todo_list` reads only `todos.txt` and shows a `[plan:N steps]` *marker* (count, not body); the full plan is fetched on demand via `todo_get_plan(id)`. This is the context-hygiene boundary: a 16-task list costs one short line each, and a multi-hundred-token plan enters context only when the model is actively working on that one task. Three implementation rules: (1) the list store stays plain-text/editable (don't bury it in JSON); (2) the detail store uses `zay.json_encode(plans, {pretty=true})` so it is human-readable and round-trips cleanly via `zay.json_decode`; (3) the key linking them is a stable identifier persisted in the list store itself (the `id:N` todo.txt key:value tag — promoted to `t.id` in `parse_line`), NOT the array index, because `table.remove` shifts indices on delete while ids stay valid across edits. `load_todos()` reads fresh from disk on every call (no `_G.todos` cache across turns) so external edits to `todos.txt` are always reflected — the old cache-once behavior masked out-of-band edits. `load_plans()` returns `{}` on missing-or-corrupt so a bad sidecar never blocks the task list.

### Plugin bridge function pattern

All `zay.*` bridge functions are C-callable `lua_CFunction` registered in the `zay` global table by `registerPluginApi()` in `sandbox.zig`. Each function receives `?*c.lua_State`, extracts arguments via `bridge.pullValue()`, performs the operation through Zay's safe Zig APIs (path validation via `sanitizePath()`, shell execution via `pwsh_exec` / `bash_exec`), and returns results as Lua values. The `std.Io` instance is stored in the Lua registry (`zay_io`) for filesystem access. Currently 29 bridge functions across 6 categories: Filesystem (11: `read_file`, `write_file`, `edit_file`, `search_files`, `find_files`, `list_dir`, `file_info`, `mkdir`, `copy_path`, `move_path`, `delete_path`), Shell & Env (5: `run_shell`, `run_bash`, `get_env`, `get_cwd`, `get_project_root`), Git (6: `git_status`, `git_diff`, `git_log`, `git_branch`, `git_add`, `git_commit`), Plugin System (4: `require`, `register_tool`, `on`, `think`), JSON (2: `json_decode`, `json_encode`), plus `shell_quote`. The registration table in `sandbox.zig` is the source of truth when adding more. Relative module loading is provided via `zay.require(mod_path)` (scoped strictly to plugin directory and cached in `zay_loaded_modules`). The JSON bridges — `zay.json_decode(str)` and `zay.json_encode(value, opts?)` — let plugins parse and emit structured data without hand-rolling a parser or shelling out to `jq`. `json_decode` reuses `pushJsonValue` (Zig `std.json.Value` → Lua); `json_encode` traverses the Lua value with `lua_next`, inferring array vs object from key shape (`lua_rawlen == lua_next` entry count → array `[...]`, else object `{...}`), and writes to an allocating writer with optional `{pretty=true}` for indent_2 output. Empty tables serialize as `[]` (the common plugin convention for an empty list). Functions/userdata/threads (no JSON form) emit `null` rather than failing the whole encode. The encode helpers (`writeLuaValueJson`/`writeTableJson`/`writeTableAsArray`/`writeTableAsObject`) share an explicit `JsonWriteError = std.Io.Writer.Error` to break the inferred-error-set dependency loop created by their mutual recursion.

- **Plugin cwd resolution:** All plugin cwd resolution goes through
  `bridge.resolvePluginCwd` (`src/lua/bridge.zig`), which reads
  `plugin_cwd_slot` (lane worktree OR `/resume` session cwd) or falls back to
  the process cwd. Never call `std.process.currentPathAlloc` directly in a
  bridge.
- **Event callback cwd window:** Plugin event callbacks (`on_started`/`on_finished`)
  run inside `runAll`'s `plugin_cwd_slot` window, set around the whole batch
  and refreshed by `rerootFromRequester` on mid-batch lane ops. This ensures
  fs/shell/git bridges called from event handlers see the correct effective cwd.

Plugin cwd resolution uses `bridge.resolvePluginCwd` (`src/lua/bridge.zig`) and the derived binding above, never `std.process.currentPathAlloc`. The effective cwd may be a lane worktree or a resumed session root; the process cwd remains the launch directory.

- **Lua C-stack manipulation:** When building a Lua table of results from Zig, the results table must stay on top of the stack across every entry. The correct idiom is `newTable()` (push table) → push entry fields + `lua_setfield(L, -2, ...)` → `lua_rawseti(L, -2, n)` (pops the entry, leaving the table on top). A stray extra push before `lua_rawseti` with the wrong table index (`-3` instead of `-2`) writes the bare integer into `results[n]` instead of the entry table and **leaks one table per match** onto the stack. Annotate the expected stack layout (`[ ... | results_table ]`, `[ ... | results_table | entry ]`) at each push/pop site so the balance is auditable.

- **`sanitizePath` realpath re-check mirrors `validateCwd`.** `sanitizePath` (`plugin_api.zig`) does a lexical `startsWith(cwd)` check, then a best-effort `std.c.realpath` re-check so a symlink escaping the project root is caught. `realpath` returns null on ENOENT (a new file being written), so fall back to the lexical verdict on null — never reject a legitimately-new path. This mirrors the bash tool's `validateCwd`. `sanitizePath` (the `bridges/shell.zig` SSOT, re-exported by fs.zig) also rejects C0 control bytes (`< 0x20`) with `error.InvalidPath`: NT returns `OBJECT_NAME_INVALID` for them and std's Io layer *panics* on that status in Debug, so a plugin path with an embedded control character (e.g. a `\t` that survived a Lua string literal — backslash paths in Lua scripts become escapes) must be rejected at the boundary instead of crashing the host. Corollary: never embed a native backslash path into a Lua script string; use forward slashes.

### Plugin Discovery Lifecycle

Project-scoped Lua plugins are discovered **once** at App startup via `PluginManager.init` → `syncPluginConfig` → `loadAll`; `.zay/plugins/*` is retained only as a **legacy fallback** root; the project root is `<cwd>/plugins/*`, which is loaded last so it overrides globals — the checked-in `plugins/` directory therefore *is* the project plugin root, and its `packages/` subtree is distribution/catalog content. The loaded set is immutable mid-session to avoid two free hazards:

- **Lua state frees:** unloading a plugin calls `PluginInstance.deinit`, which destroys its sandboxed Lua state. Any lane worker mid-dispatch through a plugin handler would be killed.
- **Registry tool-record frees:** `registerPluginTools` (`src/tui/provider_model.zig`) strips all `lua__`-prefixed tools from the shared `ToolRegistry` before re-adding. A worker dispatching through a tool record that `removePluginToolsWithPrefix` just freed is a use-after-free.

There is exactly **one** mid-session exception: a guarded cross-project `/resume`. When `createRuntime` detects `cross_project` (session cwd differs from the current runtime's cwd), it runs:

1. `anyLaneTurnActive` guard — iterates every lane; if any has a turn in `.active` or `.interrupting` state, the switch is refused with `error.InFlightTurn`. The guard runs synchronously on the UI thread with zero yield points, so no idle→active transition can interleave.
2. `syncPluginConfig` — applies the reloaded project's enable/disable + settings (build-then-swap: error leaves the previous set intact).
3. `repointProjectDir` — unloads old project plugins by directory prefix (with separator-boundary check), frees both project roots, and loads the new project's project-local roots. Re-scans the global dir for plugins that were shadowed by the old project and are now absent.
4. `registerPluginTools` — strips the previous `lua__` generation and re-adds from the live manager (idempotent; descriptor-build failure leaves the stale-but-valid set).

Global plugins (loaded from `~/.config/zay/plugins/` or `%APPDATA%/zay/plugins/`) are never touched during a repoint — their Lua states, event subscriptions, and `require` caches survive the switch. New-project plugins that share a name with a global override the global (mirroring `loadAll` semantics).

Known limitation (narrowed 2026-09-24): live lane clients keep their spawn-time `tools_json` until rebuilt — the cross-project switch now rebuilds all turn-free lanes via `refreshAllLaneTools` (see § Cross-project session resume pattern), but mid-session MCP/plugin changes still reach only newly-created or live-viewed clients.


## Durable skill context

`Agent.skill_context` owns the first admitted body for each case-insensitive skill name. Inline expansion and correlated successful model tool results activate it only alongside message admission; allocation/admission failure rolls back prepared additions. Repeated model calls retain one result per call and return `loaded_notice`.

`skill_context` session entries are complete versioned snapshots on the active branch path, including ancestors before a compaction boundary. They never project as chat messages. `SessionWriter.conversation` quiesces once to project messages and metadata together; `Agent.replaceConversation` reconstructs unambiguous legacy activations and reserves message capacity before replacing either live owner. Reconstructed entries are marked dirty for persistence. Metadata enqueue failure preserves admitted history and the dirty ledger for retry; compaction and branch navigation flush metadata before changing the active path.

`context/skill_history.zig` recognizes generated inline prefixes and successful results correlated with explicit skill calls. Historical successful results remain authoritative when the current skill file changes. Request assembly retains full skill results with their original call IDs and adds missing ledger bodies before conversation history, preserving call/result adjacency. The ledger-aware estimator counts those same bodies and rendered pruning markers. Summarizer serialization replaces full instructions with activation notices only when the persisted branch metadata contains an exact copy; unretained bodies keep their ordinary summarizer representation. Ordinary tool pruning and provider message schemas retain their existing behavior.

The ledger rejects additions exceeding 256 entries, 256 KiB per body, or 1 MiB aggregate instruction bytes. It never evicts active instructions. JSON decoding is transactional and bounded for worst-case escaping. UI activation rows deduplicate against UI-owned transcript state; idle transcript reconstruction restores the branch inventory without reading worker-owned state during queued submission.

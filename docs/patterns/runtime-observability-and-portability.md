### Toast notification pattern

A generic, thread-safe toast bus any subsystem can push to — **not** logger-specific (future pushers: MCP connect/disconnect, lane spawn/merge, background jobs, permission denials). Two decoupled pieces: `ToastBus` (`src/tui/toast.zig`) — a global ring buffer (`global`, a singleton because the logger is itself a global cross-thread struct); and `Widget` — a passive top-right overlay (no focus, no key capture). Key files: `src/tui/toast.zig` (`push` cross-thread entry, `drain` UI-thread entry), `lib/logger.zig` (`Options.toast_sink: ?*const fn (std.log.Level, []const u8) void` opaque callback — logger stays TUI-agnostic, no `lib → src` dependency), `src/root.zig` (`toastSink` adapter maps `std.log.Level`→`toast.Level`; `resolveStderrLevel` returns `?Level` so `stderr_explicit` distinguishes env-set from default), `src/tui/lifecycle.zig` (`handleTick` drains the bus; `should_tick` keeps polling while `toast.global.hasToasts()`), `src/tui/root_layout.zig` (toast child at `z_index = 4`, above all others)

**Routing in `logger.dispatch`:** warn+ goes to the toast sink when one is installed AND `stderr_explicit` is false (the TUI-tearing fix — stderr bytes land in the alternate screen and tear the frame); when `ZAY_LOG_STDERR_LEVEL` is set, warn+ goes to BOTH stderr and the toast; with no sink (headless/tests) stderr keeps the default gate. **Push-path discipline:** `push` allocates NOTHING — `Item.msg` is a fixed 1024B inline buffer (`@memcpy` truncates), so worker threads never touch the heap here. Locking is `std.Io.Mutex` (NEVER `std.atomic.Mutex` — that's a spinlock, see [Concurrency and event ownership](#concurrency-and-event-ownership)); `push`/`drain`/`dismiss` all `lock(io) catch return` (a failed lock drops the toast, never panics). `hasToasts()` is a deliberate lock-free `count > 0` read used only as a visibility hint — a stale value at most delays/advances one frame. **`drain` is called twice per visible frame** (once in `handleTick`, once in `Widget.draw`) — both take the lock; the second is effectively a no-op if the first cleared the ring, which is the intended cadence. **Config:** the `toast` section mirrors `context` (`parseToast`/`writeToast`/`hasNonDefaultToast`/`applyToastOverlay`) — all fields optional, section omitted from config.json at defaults. Out-of-range `durationMs`/`maxVisible` are **dropped** (left null) at parse, NOT clamped — distinct from the `threshold` clamp in the compaction pattern; a typo can't produce a toast that never dismisses or a stack covering the screen. Only `enabled` is surfaced in the `/settings` General tab (applied live); `durationMs`/`maxVisible`/`position` are config-file-only. `position` is reserved (only `top-right` rendered today). **`initialized` guard:** `ToastBus.init` sets `initialized = true`; `push`/`drain`/`hasToasts` early-return when false, so calls before `tui.run` inits the global (e.g. a test driving `handleTick`) are safe no-ops rather than touching an uninitialized `io`/mutex.

### Logging implementation

- **Sinks:** In Debug mode, logs go to both `zay.log` and stderr. In Release builds, logs go to stderr only (`warn` level and above by default). The file-writer thread is Debug-only (`logger.enabled_file`); the stderr sink is compiled in all builds, so the shipped ReleaseFast binary keeps an operational trail. Every line carries an ISO-8601 UTC timestamp prefix (`lib/logger.zig` `formatTimestamp`, via `clock_gettime(REALTIME)` — no `Io` handle available in the writer thread / pre-init path).

See [Toast notification pattern](#toast-notification-pattern) for sink routing and [Configuration](../config/README.md#environment-variables) for `ZAY_LOG_FILE`, `ZAY_LOG_STDERR_LEVEL`, and `ZAY_LOG_MAX_BYTES`.

- **Diagnostics:** To see all logs in release: `ZAY_LOG_STDERR_LEVEL=debug zay 2> err.log`.

- **Use `warn`, not `err`, for logged failures.** Zig 0.16's test runner hard-wires `log_err_count == 0` as a success gate: any `log.err(...)` from a passing test marks it failed. Many tests deliberately exercise error paths, so those messages must be `warn`. The stderr sink surfaces `warn` in **all** builds including ReleaseFast, so operational visibility is preserved without tripping the test gate. Reserve `err` for nothing in this codebase today — the gate makes it unusable. The pre-init escape hatch (`dispatch` when `stderr_ready == false`) writes raw to fd 2 via `std.c.write`.

### Cross-project session resume pattern

The session DB is global (`~/.config/zay/sessions.sqlite`), so the `/resume` picker's `project` and `date` group-by modes list sessions from all projects. When a user resumes a session whose `cwd` differs from the current runtime's cwd, `createRuntimeImpl` (session_switcher.zig — reached via the public `createRuntime` wrapper) detects the cross-project case as `session_id != null and !paths.pathsEqual(cwd, current.cwd)` — path comparison is separator/case-tolerant, never a raw byte compare and does three things: (1) sets `template = null` so `initSession` loads skills and plugin prompts from the session's own cwd instead of cloning the current runtime's; (2) calls `config_mod.load` with the target cwd to reload `.zay/config.json` so MCP servers, model selection, and project-scoped settings match the session's project — the env layer is constant (process env vars don't change between projects), so the `environ_map` captured at startup (`App.environ_map`, threaded through `initRuntime`) is reused; (3) after `initResume`/`initNew` succeeds, replaces `app.cached_config` with the reloaded config and calls `mcp_manager.syncFromConfig` to reconcile MCP clients. If config reload fails, the current config is used as fallback (logged, never fatal). `switchToSession` receives `summary.cwd` from the caller (`mode_lifecycle.submitMode`) and passes it to `createRuntime` instead of the current runtime's cwd

**tools_json refresh on switch (2026-09-24):** after `registerPluginTools`, `createRuntimeImpl` calls `provider_model.refreshAllLaneTools` — it re-syncs the registry's `mcp__` records from the reconciled manager, then pushes `syncToolJson` into EVERY live, turn-free lane client (lanes mid-turn or mid-cancel are skipped per-lane: `updateTools` replaces the client's `tools_json` buffer and must not race a worker serializing a prompt). The `anyLaneTurnActive` check inside the helper is belt-and-braces — the cross-project switch already refused under it — but it keeps the helper safe for future callers. The remaining limitation is TIMING, not fan-out: the refresh pins the switch-moment snapshot; servers still `.connecting` contribute tools only via the later MCP tick (which pushes to the live-viewed runtime only), and mid-session MCP/plugin changes still reach only newly-created or live-viewed clients. A stale-advertised tool degrades in-band (`"MCP tool … failed: …"` / `"MCP server not found"` — the registry record resolves the live client at dispatch time), never dangles. Regression test: `"refreshAllLaneTools pushes synced MCP and plugin tools into a non-viewed lane's tools_json"` (session_switcher.zig).

**`cwd` ownership:** `initSession` (now `initSession(target, genesis: runtime.Genesis)` — one named birth-params struct; `initNew`/`initResume` assert the mode) dups `cwd` into runtime-owned memory (freed in `AgentRuntime.deinit`), so the borrowed `summary.cwd` can be freed by the next `reloadResumeSessions`→`resumeClear` without dangling the runtime's workspace path. Without the dupe this was a use-after-free: `repoRoot()`/`liveRuntime().?.cwd` returned the freed pointer and `manager.list`→`bindText(1, cwd)` read it — deterministic once `db.zig` bound with `sqlite_transient` (copies at bind) instead of the old `sqlite_static` (kept the pointer, deferred the read to step). `home_dir` stays borrowed (root-owned, never freed, valid for the app lifetime).

- **Cross-project `/resume` plugin repoint:** `PluginManager.repointProjectDir` repoints project-scoped plugin discovery (`.zay/plugins/`) under an `anyLaneTurnActive` guard — if any lane has a live turn, the switch is refused (`error.InFlightTurn`). Unloading Lua states and stripping tool records from the shared registry while a worker dispatches through them is a use-after-free hazard (`openPlugins` must NOT call `registerPluginTools` for the same reason). Global plugins and their states, event subscriptions, and require caches are never touched. Re-registration goes through `registerPluginTools`' idempotent strip+re-add only when no lane is mid-turn.

- **Session resume segfault (null `model_id`).** Crash at `src/ai/openai_compatible.zig:100` (`gpa.dupe(u8, config.model)`; `EmptyModelId` guard at `:78`) when a null `summary.model_id` flows into `ModelSelection.custom.model.id` (non-optional `[]u8`). Guarded at three entry points: `runtime.applyFromConfig` skips attachment on empty `model_id`; `tui.applySelectedModel` returns `error.EmptyModelId`; `writeRequestPayload` returns `error.EmptyModelId`. Always use a real early return, never `std.debug.assert` — `unreachable` is UB in ReleaseFast. Previous fix: `da7c761`.

### Text-emitted tool calls recovered pre-persist (T1/T2/T3)

Some function-calling models (ling-3.0-flash, weaker gateways) emit valid tool *intent* as literal text inside a `{"type":"text"}` block (`<tool_call>bash<arg_key="command">…</arg_key></tool_call>` or `<tool_call>{"name":…,"arguments":{…}}</tool_call>`) instead of structured `tool_calls` deltas. The stream parser only reconstructs structured deltas, so such a turn has zero `.tool_call` blocks and the agent goes idle as if the model said nothing. Recovery (`recoverTextToolCalls` / `injectRecoveredToolCalls` in `src/agent.zig`, parser in `src/ai/text_tool_call.zig`) runs in the narrow window BETWEEN `collectToolCalls` and `takeAssistantMessage` in the turn loop (`Agent.run`) — it MUST run there because `takeAssistantMessage` invalidates `turn.assistant` (`= undefined`), and `hasWireContent` is `true` for a text-only message, so by the `len == 0` site the message is already gone. Ownership: `recoverTextToolCalls` returns freshly-allocated `ToolCall`s (their `call_id`/`name`/`arguments` are minted in the parser), `injectRecoveredToolCalls` appends them as new `.tool_call` ContentBlocks reallocating the content slice, and the SAME `recovered` slice drives execution (no re-collect). This mirrors `collectToolCalls`'s aliasing contract (slice shell caller-freed; element strings belong to the message). Conservatism guards: only fires when structured calls are zero, only scans `.text` blocks, and the parser only matches the explicit `<tool_call>` envelope — free-form angle brackets are never misread. The system prompt (`<tool_calling>` block) also directs compliant models never to emit tool calls as text (T2), so this is a safety net for models that ignore the directive.

### LLM request diagnostics carry model identity (L1/L2/L3)

Payload head/tail logging lives in `src/http.zig` (`http.logBytesHead` / `logBytesToolsTail`, called by `ai/transport.zig` on behalf of both wire clients and by the codex transport). The old `logBytes` truncated at 12KB head-only; because JSON key order is `model → messages → … → tools`, a realistic system prompt + a few turns already consumed the head, hiding the `tools` array (the most-wanted field when debugging tool-calling). It now appends a tail slice starting at `"tools":` when truncating, so the array is visible without reverse-engineering the payload from test fixtures. Callers must `defer`-free only when `result.ptr != bytes.ptr` (short bodies alias through). Separately, the no-tools signal is a transport flag on the client (`transport.zig` — "true when the client carries no tools; drives the `no_tools` info") and the warning carries the model id only; the URL rides a separate info log (`openai_compatible.no_tools client model= url=`) emitted on the prompt path — together they disambiguate the intentionally tool-less summarizer/naming clients from a tools-less main client.

### Streaming tool-call cap pattern

Chat-completions `stream_parser.zig` carries a **hard** cap (`tool_call_array_cap = 64`) and a **configurable** cap (`stream_part.StreamLimits.max_parallel_calls`, default 16 via `ai.default_max_parallel_tool_calls`; `ai.Config.max_parallel_tool_calls` accepts 1–64 at parse). The hard cap protects fixed `remapped_slot[64]`/`is_remapped[64]` arrays and still aborts with `error.TooManyToolCalls`. The configurable cap is a *drop* gate: deltas whose logical index is ≥ `max_calls` are parsed to completion (so later argument chunks for the same dropped call do not corrupt the SSE stream), counted in `ToolCallStream.dropped`, and skipped without touching `builders` or observer callbacks. The turn therefore completes with the first `max_calls` calls instead of failing entirely. The final `readStream` log line (`readStream.dropped`) surfaces the count. The Responses-API client has the SAME cap/drop logic since the `StreamEnv`/`StreamLimits` unification (`responses_events.StreamState` counts `dropped`), and since 650d015 its `finish` also applies the executable-arguments verdict — see **Executable-arguments verdict & truncation parity** below.

- **Streaming SSE Tool Call Deduplication & Parallel Remap:** In `src/ai/stream_parser.zig`, tool call names and IDs are atomic in streaming — first complete value wins; subsequent deltas are ignored. This deduplicates repeated names and prevents cross-tool concatenation. Some providers reuse `index: 0` for all parallel tool calls; `ToolCallStream` detects this by comparing tool-call IDs (always unique). When a new ID arrives at an occupied logical index, the call is forked into a new physical builder slot. Argument continuation deltas (no ID) route through the remap to the correct slot. Limitation: if the provider omits IDs entirely, collision detection is impossible and the second call is lost (first writer wins for the name). The over-cap reject logs the offending model id alongside the index/cap (L3) — both adapters take a `stream_part.StreamEnv{limits, id_seq}` whose `StreamLimits` carries the borrowed `model_label` used only for that log, and the SAME cap now applies to the Responses API (`responses_events.StreamState` counts `dropped`, logged at `finish`).

### Executable-arguments verdict & Responses-path truncation parity (2026-09-19)

`stream_parser.argumentsAreExecutable(raw)` (`src/ai/stream_parser.zig`) is the ONE verdict for "will these arguments dispatch as valid tool-call JSON": `sanitizeToolArguments` collapses empty/severed input to the literal `"{}"`, so the verdict distinguishes a deliberate `{}` (trimmed raw is exactly two chars) from a provider truncation (sanitize could not round-trip to a `{...}` object). BOTH parsers apply it at finish: chat-completions at `readStream` end, Responses via `StreamState.finish` → `dropIncompleteToolBlocks` (`src/ai/responses_events.zig`) — a NAMED builder with non-executable arguments loses its eagerly-appended block and counts one `tool_calls_truncated` unit (feeds the agent's retry-once hint); NAMELESS builders lose their orphan blocks too but are NOT counted (chat parity — warn and skip). On keep-mask OOM the count is still returned with blocks KEPT (degraded count-only behavior, hint suppressed, `responses_events.truncated_count_only` log) — never fabricate a drop from a failed allocation. The codex websocket loop inherits the verdict through the same `finish`. A full-arguments `done` event heals partial deltas before the verdict (`onArgumentsDone` clears then appends the authoritative string); known latent quirk: `onArgumentsDelta` appends onto an inline `{}` → `{}{...}` (no-arg Responses calls carry inline `"arguments":"{}"`). Regression tests: `"finish drops a named responses tool call whose arguments never streamed"`, `"finish keeps a deliberate empty-object arguments call"`, `"finish drops a named call whose arguments JSON is cut mid-stream"`, `"a full-arguments done event heals partial deltas before the truncation verdict"`, `"finish drops a nameless builder's orphan block without counting it"`, `"dropIncompleteToolBlocks degrades to count-only when the mask allocation fails"` (responses_events.zig).

### Internlm severed tool-call rejoining (f4c7649)

The intern-ai/internlm gateway splits ONE tool call across multiple `tool_calls` entries: name+id at one index with the arguments payload in a separate index-less/id-less/name-less builder, or name+id at `index: 0` with arguments misaligned at a later index. `joinSeveredArguments` (`src/ai/stream_parser.zig`, runs pre-verdict) re-appends a later BARE-arguments builder (empty name AND id) onto the first named call that lacks executable arguments (`readStream.joinSeveredArguments` log) and the emptied orphan is then dropped nameless without counting. Never treat a bare-arguments builder as its own call. Regression tests: `"readStream joins severed name+id and index-misaligned bare-arguments entries"`, `"readStream drops a name-only tool call whose arguments never streamed"` (stream_parser.zig).
